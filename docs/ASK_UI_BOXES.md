# 求助：怎么把方舟**战斗界面的 UI 元素框准**（要完整、跨关卡、跨分辨率）

> 用途：贴到 MAA 社区 / 群 / issue 问。第二份求助（第一份 `ASK_FRAMEPOOL_CAPTURE.md` 已自行解决 ✓）。
> 读者：做过方舟 UI 识别 / 做过游戏 UI 检测的人。

## 目标

我们要给"AI 打关"做一个**实时标注**：把屏幕上**每一个 UI 元素的完整边框**画出来，让人一眼能核对
"程序看到的东西对不对"。要求：

- **完整**：一张手牌就要框住**整张卡**（不是只框图标、也不是只框费用数字）；
  敌人数那块要框住**那一整块 HUD**（图标 + 数字 + 底衬）；左上齿轮要框住整个按钮。
- **准**：框线要贴着元素边缘（差几个像素没关系，差半张卡就不行）。
- **通用**：换关卡、换分辨率、换界面状态（战斗/暂停/选牌/看干员详情）都成立。

## 我们现在的做法（以及为什么不准 ✗）

1. **UI 元素**：在**手标的固定 ROI** 里，取"亮像素的紧贴外框"。
   ⇒ 只对**那一屏**成立 ✗。换分辨率（我们测过 1080p / 720p）或换个界面就偏 ✗。
2. **手牌区**：用**职业图标的位置**推卡片边界 —— 图标 x 左侧 29px、右侧 146px，间距 174.6（1080p）。
   ⇒ **图标一旦有假阳性/漏检，整排框错位** ✗。今天就踩了：低阈值在地图左半边刷出 10 个"等距"伪命中，
   整排手牌框画到地图上 ✗（我们后来加了两道校验：**右锚**（手牌行右对齐，最右一张必须靠近右边）+ **关卡指纹**）。
3. 我们加的闸只能**防错**（不符就不画 ✗），不能**框准** ✗。

## 我们手上的资源

- **逐帧取图**：已解决 —— 用 MaaFramework 的 Win32 `FramePool` 直接抓模拟器窗口，
  实测 **18ms/帧 ≈ 55fps**、1920×1080，不走 adb、不干扰正在跑的 MAA ✓。
- **MAA 自带的模板**：`resource/template/`（25 组，含 `Battle/OperRole`、`BattleFlag`、`Battle/StartButton`、
  `Battle/Sanity` …）。但那是 **MAA 自己需要的几样** ⇒ **不覆盖战斗 UI 的全部元素** ✗。
- **MAA 的任务 ROI**：`resource/tasks/tasks.json` 里每个任务有 `roi`（相对 **1280×720**，如
  `BattleKills.roi = [50,0,100,40]`、`BattleCostData.roi = [1199,494,80,44]`），以及 `isAscii`（数字走字符模型）。
  我们已经在用这些值读数字 ✓（`PaddleCharOCR` 那套）。
- **MaaFramework 的 Python 绑定**（PyPI `maafw`）✓。

## 具体想问的

**A. 要把"每个 UI 元素的完整边框"框准，推荐哪条路？**
   ① 自建模板集（从我们的帧上裁一次元素，之后模板匹配）？
   ② 训一个小目标检测（YOLO/YOLOv8 之类）——**但**：公开的方舟 UI 检测数据集/权重有人做过吗？
      我们不想自己从零标数据（训练太慢，这正是我们要避开的）。
   ③ 有现成的方舟 UI 元素坐标表 / layout 描述文件吗（比如某个开源项目里已经标好的战斗 UI 布局）？

**B. 战斗 UI 的元素布局，在同一宽高比下是**固定的**吗？**
   我们的经验是：**同一关非常准、换关就飘 ✗**。飘的部分我们已经确认有"地图不同"（这是应得的），
   但 **HUD（费用/敌人数/可部署数/手牌行）本身也会飘吗**？还是只要归一化到 1280×720 就固定？

**C. 手牌行有没有稳定的结构规律？**
   我们观察：**右对齐**、图标间距 1080p 下约 174.6px、卡高约 190px（y≈886–1077）。
   有没有更可靠的锚点（比如每张卡的**边框**、或卡与卡之间的**缝隙**）？换个张数（7/10/12 张）规律还成立吗？

**D. MAA 的 Peep（"牛牛监控/看看牛牛眼中的世界"）画出来的那些框，是"识别框"还是"元素框"？**
   它的框坐标能不能从**外部**拿到（日志 / 回调 / API）？如果能，我们就直接用它那套框了 —— 省得自己标。
   （我们扫过 `MaaCore.dll` 的 30 个导出：只有 `AsstGetImage/GetImageBgr/AsyncScreencap`，没有"取坐标"的接口 ✗。）

## 我们的判据（自己会拿来验收的）

- 手牌：11 张里每一张框都要贴住该卡的完整边界（我们有一帧人工核对过的基准，可当验收）；
- HUD：与游戏自己画的那块 HUD 边缘对齐（不是"数字的紧贴外框"）；
- 换到另一关后，HUD 仍然准（地图不要求）。

# 补充：一份专家意见 + 我们的实测反馈（2026-09-19 晚）

## 已采纳的判断

1. **不上 YOLO** ✓ —— 缺的不是"有没有这个东西"，而是**从识别结果恢复 UI 的几何边界** ✓；
2. **MAA 的 `roi`/template 坐标 ≠ UI layout** ✓（它是"识别用的搜索范围"）—— 拿它直接画框必然
   出现"识别 ROI"与"视觉元素框"不一致 ✓；
3. **按 1280×720 逻辑画布维护一份 UI layout** ✓，比每帧重新找 HUD 可靠得多；
4. **职业图标是内容、不是卡片几何** ✓（我们已经在改）；
5. **要的是 UI **容器**边界（边/阴影/遮罩形成的不连续）**，不是"亮像素的紧贴外框"（那是内容剪影）✓。

## 我们按建议实测了两版"边缘投影分卡"，都失败 —— 这条在本 UI 上不成立 ✗

- **v1（列方向的 Sobel 累积找峰值）**：得到 32 个峰值，被**卡内内容**（立绘/文字）污染 ✗，
  拟合出 N=7 / 步距 207（真值 N=11 / 174.6）✗。
- **v2（只留贯穿整卡高度的竖线：高瘦核开运算）**：**全屏只剩 1 条**候选 ✗。
  ⇒ 结论：**方舟手牌是紧挨着的、卡缝对比度极低**，靠"竖缝"分卡分不出来 ✓
  （真值：11 张、右锚 ≈1893（1080p）、步距 174.6、卡高 ≈190）。

## 我们现在能用的（已验收）

- **手牌**：职业图标锚点 + 三重闸（**右锚**：最右一张必须靠近右边 ✓／**等距** ✓／**必须落在手牌行带内** ✓），
  在人工核对过的基准帧上 **11/11 正确** ✓。图标只当**锚点**，不当几何来源 ✓（这点与外援一致）。
- **HUD**：目前仍是"手标 ROI 里取亮像素外框"✗（内容剪影，不是容器 ✓）—— 这是下一步要换的。
