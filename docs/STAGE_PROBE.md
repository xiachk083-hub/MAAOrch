# 关卡检测工具（Stage Probe）

> 状态：Lab 验证完成，待并入项目正式功能
> 用途：检测账号在某关卡**能否刷取**（全权委托/代理可用性），批量判定，支撑产线规划

## 1. 背景

MAAOrch 需要知道**每个账号在哪些关卡能刷**（尤其剿灭的三态：能刷/刷不了/刷完），才能规划产线（哪个账号刷哪个关卡）。

人工判定成本高（40+ 账号 × 3 关 × 每次进游戏看）。本工具用 **MAA 导航 + 外部截图判定** 自动化完成。

## 2. 检测原理

```
启动模拟器 → MAA StartUp(登录) → MAA Fight 导航到关卡详情页
    → 截图 → 判定（三态）→ 记录结果
```

关键点：
- **导航**：用 MAA 自身导航（`Fight` 任务，`times=0`）— 复用 MAA 的关卡寻路能力
- **判定**：外部截图 + 模板匹配 / 像素分析（不依赖 MAA 内部状态）
- **不修改生产配置**：lab 模式独立运行（独立实例目录、独立进程）

## 3. 判定逻辑（三态）

| 状态 | 判定依据 | 说明 |
|------|------|------|
| **能刷** | PRTS ROI 内高亮图标模板匹配分 ≥ 0.4 | 全权委托可用（金色高亮图标存在）|
| **刷不了** | 匹配分 < 0.4 | 全权委托不可用（需先手动代理/未解锁/未 400 杀）|
| **刷完** | 不在详情页（导航失败）| 本周已打完/无法前往 |

### 3.1 核心判据：PRTS ROI 模板匹配

- **区域**：`ROI = (876, 532, 183, 123)`（"开始行动"按钮上方，全权委托按钮区）
- **模板**：`UsePrts-AnnihilationSuccess.png`（金色"全权委托已激活"图标，56×33）
- **阈值**：≥ 0.4 = 能刷；< 0.4 = 刷不了

**为什么限定 ROI**：MAA 全屏匹配在刷不了的账号上会误匹配到其他金色元素（score 高达 0.992），限定 ROI 后刷不了账号只有 0.248 — 分界清晰。

实测分界：

| 账号 | 匹配分 | 判定 | 人工确认 |
|------|------|------|------|
| 官-2 外环 | 0.640 | 能刷 | ✓ |
| 官-3/12/21/33/38 | 0.640 | 能刷 | ✓（全能刷）|
| 官-5/8/9/10/14/16... | 导航失败 | 刷完 | ✓ |
| 官-13 三关 | 0.248 | 刷不了 | ✓ |
| 官-4 切尔诺伯格 | 0.248 | 刷不了 | ✓（NEW 号）|

### 3.2 辅助判据：MAA OCR 文字特征

导航后在剿灭列表页，MAA OCR 输出的文字特征：

| 特征（OCR 文字）| 含义 |
|------|------|
| `NEW` 标记（score > 0.8）| 新号未解锁（不能刷）|
| `剿灭战模拟` | 未达成 400 杀，只能模拟战 |
| `通关XX后解锁` | 关卡未解锁 |
| `全权委托`（详情页）| 可扫荡（能刷）|

### 3.3 详情页检测（判定是否导航成功）

- 区域：`(1090-1280, 620-680)`（"开始行动"按钮）
- 金色占比 > 10% = 在详情页；否则 = 导航失败（刷完/未解锁）

### 3.4 坐标映射（手动操作时）

设备竖屏 720×1280，截图横屏 1280×720：
```
input tap 坐标 = (719 - 截图y, 截图x)
```
（仅手动点击时需要；MAA 导航自动处理）

## 6. 已知限制

1. **导航失败 ≠ 一定刷完**：可能是账号不对（模拟器上登录的不是配置账号）— 检测前确认模拟器账号
2. **存档截图状态不可控**：判定必须在受控流程下进行（MAA 导航后立即截图）
3. **中文传输编码**：脚本传输到目标机时中文可能乱码 — 脚本内避免中文字面量（用 ID/ASCII 匹配）
4. **模拟器冷启动慢**：ADB 等待 60s 可能超时（端口漂移见 6.1）
5. **启动失败循环**：实例残留会导致 `_get_free_instance` 分配不到 — 用 API stop 或重启项目（勿手动杀 MAA）

### 6.1 ADB 端口漂移（已定位）

模拟器重启后 MuMu 12 的 adb 端口可能 +1（16416→16417），缓存的 `adb_address` 失效 → 连接失败死循环。修复方向：
- 每次启动从 MuMuManager 检测端口（`detect_emu_instances`）
- 连接超时自动重检测

## 7. 扩展规划：普通关卡检测

同样的框架可检测**任意普通关卡**（不只剿灭）：

| 检测项 | 方法 |
|------|------|
| 关卡是否可进（导航成功）| MAA 导航 + 详情页检测（同上）|
| 能否代理（有无锁图标）| UnableToAgent2 模板匹配（ROI 修正后）|
| 理智消耗 / 掉落 | 日志解析（SanityBeforeStage / StageDrops）|
| 关卡解锁状态 | OCR（"未解锁"/"通关后解锁"文字）|
| 周常/日常可用性 | 导航 + 时间窗口 |

**通用化设计**（并入项目时）：
```python
# services/stage_probe.py（建议）
class StageProbe:
    def __init__(self, emu_idx, client_type, adb): ...
    def nav_to_stage(self, stage) -> bool      # MAA 导航
    def capture(self) -> np.ndarray             # 截图
    def judge(self, img) -> ProbeVerdict        # 判定（模板/OCR/像素）
    def probe(self, stage) -> ProbeVerdict      # 完整流程
```
