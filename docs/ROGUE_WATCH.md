### 5.22 演练踩出来的坑：**重启模拟器会把 adb 端口挪走**（2026-09-24 15:21，代价 8 分钟）

**怎么踩的**：用 `--apply --freeze-drill` 演练冻结第 2 级（重启模拟器）。`shutdown` 返回 `errcode 0`，12 秒后 `launch` 返回 **`{"errcode":-502,"errmsg":"mainnx request failed"}`**（VM 还在关机中）—— 但 **VM 照样起来了，只是 adb 端口从 `emulator-5554` 挪到了 `emulator-5556`**（5554 被上一轮的残留占着）。#0 的 MAA 配置写死 `emulator-5554` ⇒ **机器活着、MAA 接不上**（`设备=OFFLINE`、gui 弹「请检查连接设置 → 尝试重启模拟器与 ADB」），白停 **8 分钟**（15:21:30 → 15:30:06 回到「自动肉鸽」）。

**排查（可复核）**：`MuMuManager info -v 0` ⇒ `is_process_started=false`、`adb_port=16384`（VM 真被关掉了）；`adb devices` ⇒ 只有 `emulator-5556`；`MuMuManager adb -v 0 shell getprop sys.boot_completed` ⇒ `1`（同一台，只是换了端口）；`5554` 上什么都没有。

**修法（两个看守都加固）**
1. shutdown 后**等 VM 真关掉**再 launch —— #0 用 `MuMuManager info -v 0` 的 `is_process_started=false`；机队用 "adb 读不到 `sys.boot_completed`"（主机上 `info` 对机队实例**不可靠**：跑着的 l-1 也报 `is_process_started=false`）。
2. launch 返回非 0 就**重试**（最多 3 次）。
3. **#0 侧**再加一步 `adb kill-server`（放掉残留占用；实测正是这一步让 5554 回来）。**机队侧不能这么做**：主机的 adb 服务是 5 台机队 + 产线共用的，杀了会连坐。
4. 起来后**校准**：机队那台必须在**它自己的地址**上读得到 `boot_completed`；读不到就大声留痕「需要人看」。`restartEmu` 的返回值也从"永远 true"改成真实结果。

**同一天在机队侧又踩到第 2 个坑（l-2，15:42–15:47）**：`launch` 返回 `errcode:0` **只代表"请求被受理"**，不代表 VM 起来了 —— l-2 这次冷启动花了 **>94 秒**，而当时只等 ~90 秒就判"看不到设备"、白报一次"需要人看"。⇒ 修法：每次 `launch` 之后**等足 150 秒**（每 8 秒探一次 adb），还没起来就**重发 launch**（最多 3 次），3 次都不行才留痕交人。实测 15:47 再发一次 `launch` 后 l-2 的 `127.0.0.1:17280` 回来了（`boot_completed=1`），看守在 15:48 又把它带回 `running-ok`。

### 5.23 空转闸（relapse）：**"救得活"也会变成空转**（2026-09-24 15:16–15:42，l-2 实测）

**症状**：l-2 每隔 2~4 分钟被判一次 `fake-complete`（停在「探索終了」结算页），而**每一次救援都被时效复核记成「有效」** —— 2 分钟后它确实在跑、画面也确实动过。于是：
- `ineffective` 永远是 0 ⇒ 那条"连续无效才交人工"的闸门永远不响；
- `frozenShots` 被**自己这次动作**清零（重拉 MAA / 关客户端都会让画面变一下）⇒ 冻结阶梯永远停在第一级；
- 结果：机器 2 分钟一轮地被"救"到天荒地老，号一秒没刷，动作配额照烧。**"进程在写日志" ≠ "活儿在往前走"，"救得活"也一样。**

**判据（`lib/rogue_plan.mjs`）**
- 只算「**连着**复发」：同一形态在过去 1 小时内的动作里，相邻两次**间隔 <15 分钟**才算一轮空转；
- 连着 **≥3 次**（即 2 个紧邻间隔）⇒ 升一级动作（`killgame-restart` → **`restart-emulator`**）；
- 连着 **≥6 次** ⇒ 交人工 + 现场图（连模拟器级都没治住）；
- 只对"救援形态"生效（`FAIL_KINDS`），`running-ok` 这类不算；
- **只在"上次救援被复核有效"（`ineffective===0`）时启用** —— 真的环境事件里救援会被判"无效"（画面根本没动），那一类交给上面的**集群规则**处理。两类判据互不重叠，谁也不会把谁盖掉。
- **位置**：放在「环境事件」那条**之前** —— 旁边还有一台在抖（集群=2）也照样升这一台，因为"连着复发 5 次"是单机毛病，比"同轮 2 台异常"更具体。

**为什么这样定阈值**（两条老教训都要守住）
- 2026-09-24 02:45：「环境事件别逐台静默」⇒ 本闸**不停手**，只升级动作强度；真环境事件被 `ineffective` 挡板分流。
- 2026-09-24 09:45：「救得活的机器别停」⇒ 只算**紧邻**复发；同一形态每隔 20~30 分钟犯一次、每次都救活了，**不升级**（自测里专门留了这两条老夹具）。

**自测**：决策 **90 条全绿**（G 段 10 条：2 次不升 / 3 次升模拟器级 / 6 次交人工 / 只有 2 次同形态不升 / 1 小时前的旧记录不算 / 间隔 20 分钟不算 / ineffective=1 不算 / running-ok 不升 / 理由带复发次数 / 6 次连着交人工）。
