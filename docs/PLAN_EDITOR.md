> 单文件 HTML；双击/浏览器打开即用；手机上也能开、能编辑。
> 生成器：`tools/viz_plan.py`
>
> **本文讲"一关怎么画、怎么改"；"一个账号一次生成整个活动（工作区）"见
> [`WORKSPACE.md`](WORKSPACE.md)** —— 那边管账号/活动导航、候选作业、`cleared.json` 落盘与跨账号差异对比。

> 闭环（修改树/规则入库/反哺）、关卡逻辑、账号分组见 [`JOB_SYSTEM.md`](JOB_SYSTEM.md)。

## 一、它是什么

把一份 MAA 作业（`opers` + `actions`）与**这一关的真实关卡数据**叠在一起画出来，让你在**跑之前**就看清：

- 敌人从哪来、走哪条路、**几点到门**（**BFS 算出的真实路径** + **移速算出的到门时刻**，不是示意）
- 每个干员下在哪、朝哪、下场次序是第几
- 干员射程能盖到哪些格（是否盖住敌人路径）
- 冲突：位置重叠 / 没人打冰淇淋机
- **时间轴动画**：拖动/播放，看每只怪在路径上走到哪、**已经漏了几只**

并且**可以直接在图上改**（挪位置、切朝向、调顺序），改完导出成可跑的作业 JSON。

## 三、界面（四块）

```
┌──────────────────────────────────────────────────────────────┐
│ 顶部工具条: 排轴可视化 | [作业下拉] | [导出当前作业 JSON]        │
├───────────────┬──────────────────────────┬───────────────────┤
│ 左: 出怪顺序   │ 中: 地图                  │ 右: 干员放置       │
│ T+/只数/route/ │ 格型着色 + 路径虚线 +     │ 编号/干员(职业)/   │
│ 敌人名        │ 出怪口/门/冰淇淋机 + 干员 │ 位置/朝向/↑↓ +     │
│ （颜色↔虚线） │ 标记(序号+朝向箭头)       │ 冲突提示           │
└───────────────┴──────────────────────────┴───────────────────┘
```

- **左列**：把这一关的出怪按 `T+` 排序列出（只数、走哪条 route、敌人名、**→T+ 到门时刻**）。行首圆点颜色 = 地图上那条虚线的颜色 ✓
- **中间**：地图。浅=地面、深=高台、灰=虚空；`S`=地面出怪口、`✈`=飞行出怪口、`G`=蓝门、`❄`=装置（如 ex02 的冰淇淋机 [5,3]，按关登记）
- **地图下方**：**时间轴播放条**（▶播放 / 拖动 = 时间轴）。每只怪按 `出怪 t → 到门 arrival` 线性插值，用 route 同色圆点画在路径上；右侧实时显示 **「已到门 N 只」**（就是漏怪数）
- **右列**：干员放置表（动作序列），每条带序号 + ↑↓ 按钮 + 冲突清单

## 四、能做什么（操作全表）

| 想做的事 | 操作 |
|---|---|
| **挪位置** | 点干员（高亮=选中）→ 点地图目标格。会校验：不可部署格 / 职业与格子类型不匹配（远程需高台、近战需地面）→ 弹提示拒绝 |
| **切朝向** | 再点一次同一个干员 → 朝向循环（↑→↓←） |
| **调顺序** | 右列列表**拖动**该项到目标位置（拖动中半透明、目标行上方黄线）；或用 **↑↓** 做 1 格微调 |
| **看冲突** | 任何改动后**实时重算**：位置重叠 / 装置覆盖（如 ex02：无人站 [5,2]/[5,4] 就打不到冰淇淋机 [5,3]） |
| **看到门时刻** | 左列每条出怪后面标 `→T+X`（= 出怪 + 步数÷移速）；缺数据标"移速缺失/路径缺失"，飞行标 `≈直线` |
| **看威胁时间轴** | 地图下方播放条：▶ 播放 / 拖动。圆点在路径上移动，右侧报「已到门 N 只」——**用来一眼看出某时刻漏了几只** |
| **导出** | 顶部「导出当前作业 JSON」→ 下载含全部修改的 MAA 作业 |
| **切作业** | 顶部下拉，装的是**这一关池子里的全部作业**；标签 = `作业名｜文件名`（同名作业靠文件名区分） |
| **导回** | 导出的 JSON 用 `python tools/viz_plan.py --ingest` 收编进池子，下次生成自动进下拉 |

**编辑会自动存在浏览器本地**（`localStorage`，键 `vizEdits2_<stage>`，内部按**作业的源文件路径**分槽）
→ 刷新不丢 ✓，而且池子里增删作业**不会把编辑串到别的作业上**（旧版按下标存，会串）；
换浏览器/清缓存会丢（想清空：F12 控制台 `localStorage.clear()`）。

> 旧键 `vizEdits_<stage>` 是按下标存的，池子一增减就会错位回填，已弃用、不再读取。
> 启动时不写盘（只读），所以任何一次读取闪失都不会反过来覆盖你的编辑。

## 五、数据从哪来

| 数据 | 来源 |
|---|---|
| 地图格型（地面/高台/虚空/出怪口/蓝门） | `data/_level_<stage>.json` → `mapData.tiles/map` |
| 敌人路径 | 用可走格做 **BFS**（起点→终点最短路径）——route 只给端点，路径是算出来的；**BFS 失败 = 飞行单位**（跨不过地形，例：第 3 列整列不可走），改用起终点**直线近似**（标注 `≈直线`） |
| 出怪时刻/只数/敌人名 | `waves[].fragments[].actions[]` + `data/_enemy_db.json` 查名字 |
| **敌人移速** | `data/_enemy_db.json` → `Value[level].enemyData.attributes.moveSpeed.m_value`（本地就有，不用抓 Wiki）。换算见下 |
| 射程 | **MAA `resource/battle_data.json`** → `chars[id].rangeId` → `ranges[rangeId]` 的偏移列表 |
| 作业 | 这一关的池子：`data/copilot/<stage>/` + `<stage>_edited/` + `*//<stage>_*.json`（也可用命令行指定任意 JSON） |

### 到门时刻怎么算的（`tools/enemy_speed.py`）

```
到门时刻 = 出怪时刻 + 路径步数 ÷ 移速        路径步数 = 格数 - 1
```

**换算系数 = 1.0，即 `moveSpeed` 本身就是「格/秒」—— 这是实测对账出来的，不要改成 0.5：**

| 路径 | 敌人 | 步数 | 模型算出 | 实测 | 判定 |
|---|---|---|---|---|---|
| 右路 (10,1)→(10,5) | 寻路者精锐战士 moveSpeed=1.1 | 8 | **T+10.27** | 约 T+10 | ✓ |
| 左路 (2,6)→(0,1) | 战术猎犬pro moveSpeed=1.9 | 7 | **T+13.68** | ~~T+16~~ | 见下 |

> 流传的「原始值 × 0.5」在这个数据源上被实测否掉：右路会算出 T+17.5，与实测差一倍。
> **换数据源必须重做对账**（`python tools/enemy_speed.py` 会跑 `reconcile()`）。
>
> ⚠️ 顺带纠正一处旧账：`docs/GA_EX2_阶段汇总_20260916.md` 记的「左路约 T+16 到门」
> 等于 `7 步 ÷ 1.1（寻路者速度）＋ T+10`，但**左路 T+10 出的是战术猎犬（1.9）**，
> 实际 7/1.9 = 3.68 → **T+13.68**。方向上是"左路比记的更早到"，不改变那份文档
> "开局顺序错了"的结论，但数字要按数据。

**act16side_ex02 的威胁时间表（算出来的）**：

| 到门 | 路线 | 敌人 | 移速 |
|---|---|---|---|
| **T+10.27** | 右路 | 寻路者精锐战士 | 1.1 |
| **T+13.68** | 左路 | 战术猎犬pro | 1.9 |
| **T+17.5** | 左门（飞行·直线近似） | 御4 | 0.8 |
| **T+37.0** | 中路 | 寻路者阵地撕裂者 | 0.6 |

**缺失一律标注、不猜**：查不到敌人 ID → `speed_missing`；路径算不出 → `path_missing`；
该 level 档位数值为 0（如御4 的 level=1）→ 回落 level 0 并标 `fell_back`。

> ⚠️ **系数 1.0 目前是「有争议的结论」，不是定论。** 关卡数据的 `options.moveMultiplier`
> 在**全部 18 关里都是 0.5**，也就是那份流传的 ×0.5 并不是编的、它是个真字段。
> 我判定 1.0 的依据是 `docs/GA_EX2_阶段汇总_20260916.md` 里那句「右路约 T+10」，
> 但那份文档把同一张表的另一行（左路 T+16）算错了 ⇒ 该表"实测"的标注不可靠，
> 所以这个锚点**可能也是推出来的**（那就成了循环论证）。
> **没有本地数据能定这个案**（`_enemy_handbook.json` 无移速字段；`level.enemyDbRefs` 全是
> `overwrittenData: null`，没有逐关覆盖）。
> **定案办法**：实跑一局 ex02，看第一只怪什么时候过门 —— 7 秒（×1.0，T+10.27）
> 还是 14.5 秒（×0.5，T+17.5），一眼可辨。在此之前，判漏结论要按两套系数各看一遍
> （`python -c "import cost_model as C; C.check_leaks('act16side_ex02', mult=0.5)"`）。

### 费用模型与判漏（`tools/cost_model.py`）

```
第 N 个部署最早落地时刻 = 等到费用够（初始 initialCost + 回费 1/costIncreaseTime 秒，封顶 maxCost）
```

数据全部本地且逐项核实过：

| 项 | 来源 | ex02 实测值 |
|---|---|---|
| 初始费用 / 回费间隔 / 上限 / 生命点 | `data/_level_<stage>.json` → `options` | 10 / 1.0 / 99 / 3 |
| 部署费用 | `_char_table.json` → `phases[<E>].attributesKeyFrames[0].data.cost` | 乌尔比安 E0/E1/E2 = 20/22/24 |
| 精英阶段 | `data/operbox_batch/emu2.json` → `elite` | 这批作业的干员全是 E2 |

⚠️ 三个坑（都实测踩过）：`initialCost` **逐关不同**（本仓出现过 3/8/10/15/18/24/25），不能写死 10；
费用**按精英阶段变**，键是 `phases[].attributesKeyFrames[0].data.cost`（`phases[].cost` 是 None）；
box 的原始键是 **`elite`** 不是 `e`（`e` 是 `box_ops()` 映射出来的，取错就全按 E0 算）。

**怎么读判漏结论（别overclaim）**：模型**不计先锋产费** ⇒ 落地只会比真实更晚，是**悲观下界**。
- `已挡` / `可打` = **确定不漏**（连不考虑产费都赶上了）——硬结论
- `存疑` = 悲观下界下够不着。**不等于一定漏**：算上产费可能就来得及

⇒ 这份输出的用处是**筛掉确定不漏的，把「存疑」挑出来人工看**，不是直接给"会漏"的判决。
右列每个部署后面标的 `T+X` 就是它的最早落地时刻（费用缺失标「费用缺失」，不参与判定）。

> 射程形状实测：`x-4`/`y-1` 这类是**对称**的（朝向无影响）；`3-6` 这类是**单向伸出**（朝向决定覆盖）。

## 七、导出的 JSON 长什么样

文件名：`<stage>__<作业名>__<日期>.json`，例 `act16side_ex02__吾导先路·复刻_-_GA-EX-2_-_限量蒙布朗_-_单核__20260916.json`
（旧版是 `edited_<下拉下标>.json`——既不含关卡也不含作业名，导两次分不清，且下标换一次生成就变）。

```json
{"version":3,"stage_name":"act16side_ex02","minimum_required":"v4.0.0",
 "doc":{"title":"…（页面编辑）"},
 "opers":[{"name":"凛御银灰","skill":3,"skill_usage":1}, …],   // ← 原样保留原作业字段（skill/练度等）
 "groups":[…],                                                 // ← 原样保留
 "actions":[{"type":"SpeedUp"},
            {"type":"Deploy","name":"…","location":[x,y],"direction":"Up"}, …,
            {"type":"SkillDaemon"}]}
```
- 部署顺序 = `actions` 数组顺序（**这就是"放置先后"**）
- 编辑新增的干员会自动补进 `opers`（`skill:1`），原有干员字段一律不动

**导出→导回这一步是「一条命令」，不是「零命令」——这是设计前提，不是没做完。**
浏览器只能「下载」：页面由静态 `http.server` 托管，**没有写接口**，写不进仓库目录
（`../copilot/...` 还会被 normpath 折回根内，实测 404）。所以落地必须由命令行做：
```bash
python tools/viz_plan.py --ingest        # 自动取 ~/Downloads 里最新的 <stage>__*.json
```
它会收编到 `data/copilot/<stage>_edited/` 并重画，下次生成就自动出现在下拉里 → **回路闭合**。

## 八、局限与注意

1. **只对已有 level 数据的关卡可用**：换关需先有 `data/_level_<stage>.json`。
   **装置坐标按关登记在代码里的 `DEVICE` 表**（`tools/viz_plan.py` 顶部，形如
   `{"act16side_ex02": ([(5,3,"❄")], [(5,2),(5,4)], "冰淇淋机 [5,3]")}` = 装置格/必须有人站的格/装置名）。
   没登记的关卡既**不画装置**、也**不报"无人站"这条冲突**——否则换关后会拿 ex02 的 [5,3] 在别的图上胡说。
   新关要判装置，往这张表加一行（装置几何是逐关的，从 level 数据推不出来）。
   ⚠️ 没有 `--device` 这个参数（早期文档写过，代码里从来没实现）；
2. **朝向只对"单向伸出"射程有意义**（如逻各斯 `3-6`）；对称射程（圣聆初雪 `x-4`、白面鸮 `y-1`）改朝向不改变覆盖；
3. **组名/占位符无法验证**：prts 作业里的"组名"（如"奶盾"）没有成员名单 → 图上不会判它，
   这类干员的职业列会显示 `?`；
4. 图上的朝向箭头与序号是**部署信息**，不是战斗中的实时状态；
5. 编辑只存**本浏览器**（`localStorage`）；跨设备请用「导出 JSON」。
   **工作区页面例外**：那条横条上的「保存为 cleared」能把当前编辑写成这一关的
   `cleared.json`（需 `tools/ws_server.py`；静态托管下自动退回导出+`--save-cleared` 收编），
   见 [`WORKSPACE.md`](WORKSPACE.md)；
6. **右列只渲染 `Deploy` / `Retreat` / `Skill` 三类动作**：`SpeedUp` 这类会被丢掉（导出时会自动补回）。
   字段名实测口径：MAA 作业里延时是 **`pre_delay`（蛇形）**，不是 `preDelay`——早期读错键名，
   导致右列的 `+Ns` 角标从来没显示过，已修；
7. **到门时刻是"直线速度"估算，不含减速/停顿**：被阻挡、被减速（冰冻/束缚）、
   飞行单位中途折向等都会让实际到门时间晚于算出的值；**飞行是起终点直线近似**（标注 `≈直线`），
   不是真实的飞行路线（关卡数据只给起终点）。所以这个数是**下界参考**，不是精确值；
8. 已修的历史 bug（供参照）：
   - 右列整块不渲染 → `ReferenceError: ai is not defined`（`forEach((a,ai)` 参数丢失）；
   - 右列被挤到下一行 → `flex-wrap:wrap`（三列总宽 > 视口）；
   - 干员名竖排 → 图层容器宽度塌缩（未给 width/height）；
   - `D.stage` 从未注入 → localStorage 键恒为 `vizEdits_undefined`（各关共用一个），
     且导出时 `stage_name` 一律回落成 `act16side_ex02`（换关导出的作业标错关卡）。
