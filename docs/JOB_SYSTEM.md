# 作业系统 —— 迭代闭环 / 关卡逻辑 / 账号分组

> 由来（2026-09-16 用户《作业系统 · 总指导》）：**核心是迭代** —— AI 生成 → 人改 → 对比 → 入库 → 反哺 → 再生成；
> **关卡逻辑**是"多作业 → 单逻辑"的转换，让新账号能按逻辑生成；
> **分组**让相似账号共享匹配。
>
> 本文覆盖闭环/逻辑/分组三层。工作区结构与编辑器导航见 [`WORKSPACE.md`](WORKSPACE.md)，
> 单关编辑器的画法与操作见 [`PLAN_EDITOR.md`](PLAN_EDITOR.md)。

## 二、修改树（闭环的原始素材）

```
<关卡>/
  versions/
    v1_ai.json / v1_ai.meta.json          ← 生成工作区时自动建（匹配引擎排第一的那份候选）
    v2_human.json                          ← 人第一次改（parent = v1_ai，changes = 改了什么）
    v2b_human.json                         ← 从 v1_ai 另开一支（同父的第 2 个子节点）
    v3_human.json                          ← 在 v2 之上继续（parent = v2_human）
  cleared.json                             ← 「保存为 cleared」时同步的那份
```

- **`.json` 是能直接喂 MAA 的作业**（不含我们的字段），**`.meta.json` 是溯源**（父节点/作者/时间/changes/备注）。
- 编号 = 深度 + 兄弟字母：`v2`/`v2b`/`v2c`，**不重排已有节点**（版本是历史）。
- 人直接改某份候选（不是改版本）时，节点仍落在深度 2，`base_src` 记下改的是哪份候选，
  `changes` 仍相对它算 —— 否则"改了哪几处"就丢了。
- 父作业读不到时 `changes=[]` 且标 `parent_missing=True`，**不假装"没改过"**。

> **改完一版之后怎么确认闭环转了 —— 一条命令**（别挨个翻文件）：
> ```bash
> python tools/ws_server.py --open                     # 起可写服务（8897）
> # 浏览器里改一版 → 写备注 → 点「保存为新版本」
> python tools/loop_check.py 9036 act54side --build     # ①树 ②规则库 ③反哺预演 ④一句话结论
> ```
> `loop_check.py` 是**只读体检**（除 `--build` 外不写任何文件），每关输出四行并给出下一步该敲什么。
> 实测通过时它长这样：
> ```
> ① 修改树：4 个节点 ｜ 人改 2 个、共 2 处（v2_human: 把 1 号位挪到 [1,1]…）
> ② 规则库：1 条（≥2 次的 1 条）　×2 location [5, 5]→[1, 1]
> ③ 反哺预演：能套上 1/1 条（基版 v1_ai）
> ④ 闭环已转（有人改 + 有规则 + 反哺能套上）
> ```

编辑器里的呈现：左列「修改树」面板列全部节点（作者/时间/改 N 处/备注），每个节点两个按钮 ——
**载入**（拉进画布继续编辑）/ **看改动**（展开 changes 列表）。保存有两条：
**保存为新版本**（只落节点）与 **保存为 cleared**（落节点 + 同步 `cleared.json`）。
另有一个 **换人** 按钮：从**这个号的 box** 里换（按目标格类型过滤近战/高台）。

命令行等价物：

```bash
python tools/workspace.py --save-version 9036 act54side SR-5            # 落节点（取下载目录最新导出）
python tools/workspace.py --save-cleared 9036 act54side SR-5 <file>    # 落节点 + cleared
python tools/workspace.py --save-version 9036 act54side SR-5 --parent v1_ai --note "左路换成双挡"
```

### 差异的两条口径（都是实测撞出来的）

1. **框架动作（`SpeedUp` / `SkillDaemon`，无站位无目标）不参与对齐**：池子里的作业常把 `SpeedUp`
   插在中间（中途加速），而编辑器导出会把 `SpeedUp` 提到最前、`SkillDaemon` 放到最后
   ⇒ 「只挪了一格」会被报成 `action_added(SpeedUp) + action_removed(SpeedUp)` **三处改动**。
   忠实，但没用，而且会让"改 N 处"这个数失真。现在只在**数量**变化时给一条低噪提示。
2. **`changes` 是相对"父版本"算的**：人改的若是 AI 根节点那份候选，父就是 `v1_ai`（树读成
   `v1_ai → v2_human`）；改的是别的候选，父为空、`base_src` 记下是哪一份。

### ⚠️ 编辑器保存必须**无损**（2026-09-16 用户质疑"框架动作边界"时查出来的）

用户问"`Skill`/`Retreat` 会不会也被当成框架动作排除"——边界本身是对的（判据 = 类型 ∈ {SpeedUp, SkillDaemon}
**且无名字**，`Skill`/`Retreat` 都带名字、都参与对齐），但顺着这条查下去发现**保存路径在丢数据**：

| 丢在哪 | 原来的行为 | 影响 |
|---|---|---|
| `normalize_job` | 只留 `(type, name)`，条件字段全丢 | 池子里 **56 份带定时 `Skill`、60 份带 `Retreat`**，条件字段（`cost_changes`/`kills`/`post_delay`/`rear_delay`）与 `doc` 注释（"本次开技能的时间为红线走到火陈右侧2格左右…"）**就是打法本体** |
| 页面导出 `jobJson` | 只 emit `Deploy` + 合成 SpeedUp/SkillDaemon | **整条技能/撤退轴丢失** —— 人保存一版，作业就废了 |
| JS 侧 `wsNormalizeJob` | 只认 4 种类型 | **读一个版本再存下去**同样销毁战术动作 |
| 动作类型白名单 | 只认 4 种（schema 里其实有 **10 种**） | `BulletTime`（1/5 速）/`ResetStopwatch`（帧级计时）被静默丢弃 —— 那正是**帧级技能轴**的机制 |

**现在的口径：逐条、逐字段、按原顺序保留。** 每个动作带 `raw`（原始字典），导出时以它为底只覆盖页面真正改过的字段
（Deploy 的 `location`/`direction`）。不认识的类型照旧搬运，页面上标 `?` 并在 tooltip 里给出原始 JSON。
另外 `opers` 只补**真干员**（判据 = 页面已有的职业表 `D.prof`）：实测 SR-EX-8 的「车」「快活」是口语占位名，
给它们造 `skill:1` 等于让 MAA 去配一个不存在的人。

**验证（浏览器真往返）**：拿 SR-EX-8（18 个动作，含 5 条定时 `Skill`、`SkillUsage`、`Output`）——
不做任何编辑直接「保存为新版本」⇒ **改 0 处**（动作逐字节一致）。这个性质是整个闭环可信的前提：
**报出来的每一处改动，都是人真的改的**。

> 顺带：`write_html()` 现在会对生成的页面跑一次 `node --check`（有 node 才跑）。页面 JS 是 Python 字符串拼的，
> 少一个括号 = 打开白屏，而症状只是"下拉框不存在"——本轮就靠这道闸门当场抓到自己写的两个语法错误。

## 三、规则入库（差异就是标注）

```bash
python tools/rules_db.py --build            # 聚合并写盘
python tools/rules_db.py --stage act54side_03 --min-count 2
```

聚合口径（**改前先读，改了就出脏数据**）：

| 口径 | 说明 |
|---|---|
| 只收 `author=human` 的节点 | AI 自己的选配不是"修正"（`v1_ai` 永远贡献 0 条规则） |
| 按 `(stage, type, operator, from, to)` 聚合 | **不按 step** —— 步数在版本间会漂移，而"把 [5,2] 的某人从 Up 改成 Down"在哪一版都是同一件事 |
| `from`/`to` 是**应用条件** | 反哺时只有作业当前状态**正好等于 from** 才动手（规则 = "看到 X 就改成 Y"） |
| `count` = 见过几次 | 越大越可靠；**默认只用 count≥2 的**（只出现一次可能只是某一次尝试） |
| 编队类差异进 `lineup` 而非 `rules` | `opers_added/removed`（"这份作业用的人被人删了"）是有用信号，但它不是位置规则，套不上 |

两份产物：`knowledge/edits.json`（**剥掉 sources/账号标识与文件路径**，note 是关卡特有打法，按知识保留）
＋ `data/rules/edits_full.json`（含 `sources`：哪个账号的哪一版贡献的，本地留档可审计）。
两条都在 `.gitignore` 覆盖范围内（`data/` 与 `knowledge/`），所以规则不会自动进公开仓库；
即使以后要公开知识库，公开的那份也已经剥掉标识 —— 别往它里面加账号 id 或文件路径。

> ⚠️ **规则是关卡级的（跨账号、跨分支）**，不是分支私有的：从 v2b 分支学到的修正，会套到 v2 分支的作业上。
> 这是有意的（stage knowledge），但意味着 `--min-count 1` 时可能把**两个分支互相矛盾的看法**一起套上去。
> 所以 CLI 在 `--min-count < 2` 时会打印警告，应用日志里也给出每条的 `sources` 数量。

## 四、反哺生成（闭环的最后一环）

```bash
python tools/feedback.py 9036 act54side SR-3 --min-count 2            # 规则套最新的人改版 → 落 vN_ai
python tools/feedback.py 9036 act54side SR-3 --min-count 1 --base v1_ai --dry-run
python tools/feedback.py 9036 act54side SR-3 --llm                    # 额外让 LLM 精修（有 token 成本）
```

- **基版默认 = AI 的根版本 `v1_ai`**，不是最新的人改版。⚠️ 这条是 2026-09-16 沙盒实测撞出来的：
  规则记的是「改前 → 改后」，把它套到**人已经改好**的最新版上，`from` 必然不匹配 ⇒ 报"套上 0 条"，
  看着像闭环没合上，其实只是基版选错对象。反哺的用途是"下次生成自动修正"——要套的是 **AI 的基线**
  （新账号就是它的 AI 选配）。`--from-latest` 保留旧行为；`--base` 可指定任意版本 / `cleared.json` / 某份候选。
- **套用是保守的**：不满足 `from` 条件的一条也不动。一条都套不上时**不写节点**并说明原因（"宁可少改"）。
- **评估复用编辑器那套判据**（把作业写临时文件 → `viz_plan.build_payload` → 读 `warns`/`verd`），
  所以"编辑器里看到的"和"反哺报告的"永远同一个口径，不另写一份判定逻辑。
- `--llm` 是**可选精修**：把部署表 + 人写过的备注交给 LLM 要一个 JSON patch，**只认**
  `deploys[].loc/dir` 两列（让模型改整份作业 JSON，它会在无关字段上编东西），且顶多改 4 条；
  任何一步不成立就返回 None 并说明原因，绝不半途改一半。默认关（有 token 成本、输出不可复现）。

## 五、关卡逻辑（多作业 → 单逻辑）

```bash
python tools/stage_logic.py --stage act16side_ex02 --threshold 0.5
python tools/stage_logic.py --stage act16side_ex02 --threshold 0.5 --generate --account 9036 --activity act16side
```

三路对齐（少一路就只剩"抄作业"）：

| 路 | 算什么 |
|---|---|
| **位置** | 格 → `coverage`（多少份作业在这站人）/ `operators`（站过谁）/ `direction`（多数朝向）/ `ordinal_median`（通常第几个下） |
| **功能** | 职业 → `block/output/heal/support/dp/special`；**医疗恒为 `heal`，绝不进伤害类** |
| **时间** | 该格的 `must_be_ready_by` = **占用窗末刻**：敌人**还在这格**的最后一刻（2026-09-16 口径定为"占用窗"）。`到达 = 出怪 + 走到第 i 格 / 移速 + 这一格之前的累计停留`，`末刻 = 到达 + 这一格自己的停留`（`WAIT_FOR_SECONDS` 是原地罚站，站着的那段时间挡位仍能拦）。停留数据来自 `viz_plan.RoutePath.waits_seq`（逐次给）。**改动前只算到达、`WAIT` 不进公式**，对停留点之后的格一律偏早 |

输出 `data/stage_logic/<stage>.json`：`necessary_positions`（coverage ≥ 阈值且 ≥2 份作业）、
`necessary_functions` / `optional_functions`、`timing`（按 ordinals 翻译成"第 k 个部署要落地"的窗口）。

**功能是读到的还是猜的，一律标出来**：占位符（"奶盾""打人近卫""高台核"）没有 profession，
只能按名字关键词归类 ⇒ 每个位置带 `func_source ∈ profession / placeholder_guess / unknown`，
汇总里 `n_func_guessed` 单列。**不标出来就等于把猜测混进"必要功能"**。

**实测（act16side_ex02，13 份样本）**：提取出 5 个必要位，其中 `[5,2] 输出 覆盖 77%` ——
与既有的几何判据（`tools/_axis_check.py` 的"冰淇淋机 [5,3] 高频覆盖位 [5,2]/[5,4]"）**独立吻合**。
两条互不相干的路径（统计对齐 vs 手工登记几何）指向同一格，这是这套提取最有力的一次交叉验证。

## 六、按逻辑生成

对每个必要位按时间顺序挑人，**每步留理由**：

1. 逻辑里**证明过的人**里有、且这个号的 box 也有的（**且功能对得上** —— 样本里可能只是"另一个功能的人恰好站这格"，
   实测 `[8,4]` 既有「奶盾」也有一名近卫，照抄名字会把近卫派到治疗位）；
2. 否则按功能挑：阻挡位跑 1v1 决斗（敌人死/挡位死 + 剩血），输出位比"射程盖到这条路几格"；
3. 兜底 = 该功能里练度最好的。

其它：方向取该格多数朝向；**技能槽从样本投票取**（写死 1 会让生成的轴在 MAA 里技能不匹配）；
产出走 `versions.add_version(author="ai")`，所以它和人的版本在同一棵树里可比。

**实测（9036 / GA-EX-2）**：必要位 5 → 落地 5 个 → 评估 **已挡 21 / 可打 0 / 存疑 3、无冲突**。

> **📌 标注（2026-09-19）——这组数字不可复现，引用前必须重跑**：
> 口径 = **9036 的 box + 单个 AI 生成方案**（`tools/v1_quality.py 9036 act16side ex02`）。
> 但 **9036 的 box 已不在 `data/boxes/`**（只剩 `data/_trash/operbox_9036_*.json`，按清理纪律那是"判过人数不符"的存疑副本，**不能当基线**）
> ⇒ 缺 box 就无法复现这组 21/0/3；要引用请先用当前号重跑同口径。
> 参考（**不同量纲，别混比**）：2026-09-19 修掉"按起点查去重表"那批 bug 后，**全池 33 份作业**的判漏翻转率
> **7.2%（judge_full）/ 7.7%（check_leaks）**、方向净"变乐观"（确定漏 183→165）——详见 `docs/CLEARING_AGENT.md` §8d-2 ⑥b。

## 七、账号分组

```bash
python tools/box_groups.py                 # 指纹 + 相似度 → data/box_groups.json
```

- 指纹 = `{干员名: 精英阶段}`；相似度 = 拥有干员集合的 **Jaccard**（另有 `--mode e2` = 只看精二集合）。
- 贪心归组（阈值 0.85，与规格一致）；每组记**代表号**与**组内最小相似度**
  （只报平均相似会把"组里有一个勉强够线的号"盖掉，而那个号最容易被共享结论坑到）。
- **同组共享的是"候选顺序"，绝不是"结论"**：`group_candidates.json` 只存每关的作业 id 顺序，
  用来排池子遍历顺序；**每个号照样重新算一遍缺人/练度/技能槽**。同组 ≠ 同一个号，
  把结论也缓存了就会出现"练度差一点的号被判成能跑"的静默错误。
- 实测（9036 与它的 94.9% 相似号）：缓存开/关挑中的候选**完全一致**，而两个号的判定各自独立。

> 诚实备注：本仓当前只有 2 个真账号，**匹配本身不是瓶颈**（全量索引 319 份 json ≈ 0.1s，一次排序 ≈ 0.05s）。
> 分组现在的实际价值是"哪些号可以共用一批候选"的可视化与顺序缓存；账号上百时它才会变成真正的省时项。

## 九、边界与注意

1. **没打过关的尝试不算样本**：`stage_logic` 默认排除自产件（`ga_derived`/`*_adapted`/「编排」），
   因为"一个没打过关的尝试站的位置"凭什么叫必要位。要一起看用 `--include-derived`。
2. **时间窗依赖移速系数**（`enemy_speed.MULT`，目前 1.0，**是有争议的结论**）：
   输出里带 `speed_mult`；看**先后关系**（谁必须在谁之前）不受系数影响，看绝对值会整体平移。
3. **不是所有关都能提取**：样本 <2 份时 `necessary_positions` 为空（那只是"没数据"，不是"没有必要位"）。
4. **规则会跨分支/跨账号合并**（见 §三的警告），`count` 与 `sources` 是判断可靠性的唯一依据。
5. **关卡数据的 `buildableType` 不是权威**：实测 SR-3 有已通关的池子作业把干员放在
   `tile_floor/buildableType=NONE` 的格上 ⇒ 编辑器只在**虚空格（`tile_forbidden`）**上硬拦，
   可走地面标 NONE 的格子放行但提示"数据存疑"（以实战为准，不以字段为准）。
6. **行原点（坐标朝向）已对账**：`viz_plan.level()` 的 `M[H-1-y]` 取法在 30 关里 **28 关胜出**
   （12 关碾压：ex02 92% vs 48%、act54side_05 98% vs 47%），换另一种行原点只有 2 关微弱胜出且样本极小
   ⇒ **现状是对的，别翻**。判据 = 近战部署落点是否落在（由 route 独立算出的）敌人路径格上。

## 十、下一步怎么决定：先看 AI 选配质量（`v1_quality.py`）

用户口径：**"改一版之前先看 `v1_ai` 质量 —— 能用只是细节不对 → 改一版；不能用缺关键位 → 先修生成端。
这个判断只有你能做，因为你知道这关该怎么打。"** 判断需要领域知识，但**原料可以客观化**：

```bash
python tools/v1_quality.py 9036 act54side          # 整个活动（按"最能用"排序）
```

每关给五行：① 选配来源+匹配结论 ② 冲突数 ③ 判漏（已挡/可打/存疑） ④ **必要位覆盖**（对照 `stage_logic`：
这一关必须站人的格被 `v1_ai` 盖住几个，缺哪几个） ⑤ 一句话评级：

| 评级 | 含义 |
|---|---|
| **差不多能用** | 必要位站全、无冲突 ⇒ 改细节才是有价值的标注 |
| **缺 1 人** | 借助战/替代能补，不一定是废弃项 |
| **有冲突** | 先挪位/补装置覆盖 |
| **要补位** | 必要位没站全 ⇒ **生成端的问题，标注救不了** |
| **缺人（≥2）** | 编队对不上，谈不上改 |

**实测（9036 / act54side，2026-09-16）**：16 关里 **5 关「差不多能用」** —— SR-4 / SR-5 / SR-EX-2 / SR-EX-3 / SR-EX-4
（必要位分别 1/1、2/2、3/3、4/4、**7/7 全覆盖且无冲突**，优先挑 SR-EX-4）；4 关「缺 1 人」（圣聆初雪，可借助战）；
其余是「要补位/有冲突」—— 那是生成端的待修项，不是标注的输入。

> ⚠️ 判漏那列是**悲观下界**（不计先锋产费）⇒ 「存疑」不等于会漏（见 `PLAN_VISUALIZATION` 的费用模型口径）；
> 必要位的功能有 `n_func_guessed` 个是**按占位符名字猜的** —— 都要当参考，不是判决。

### 规则泛化能力（量化，别 overclaim）

同一条规则（`act54side_02`：芬 `[5,5]→[1,1]`）实测命中：**同关同号 3/10 份作业**、**同关别的账号 1 处**、
**换关 0 处**。⇒ 规则是**点位级**的（关 + 格 + 干员 + 朝向全对上才生效）：
**积累靠"同一关的多次/多号修正"，不靠跨关迁移**。所以「改一版」的长期收益只在同一关内叠加 ——
这也是为什么质量体检要先挑一关"能用"的来改。

## 十一、模式污染：突袭作业会冒充普通关的候选（2026-09-16 发射前检查抓到的）

**现象**：SR-EX-4（普通关）的 AI 选配是 `102553`「SR-EX-4 **突袭**挂机作战」——**模式选错了**。

**根因**：作业站上突袭作业与普通作业**声明同一个 `stage_name`**
（`102553`/`102610` 都写 `act54side_ex04`，没有 `#f#` 后缀）⇒ 只按 `stage_name` 匹配根本分不开。
按 MAA 的玩法，突袭是 `act54side_ex04#f#`（FOUR_STAR）另一套敌人数值/数量，用错模式的轴会打不过。

**判据取权威字段，不猜关键词**：项目自己的筛选产物（`data/copilot/*screening*.json`、`*pick*.json`，
由 `tools/prts_event_pick.py` 按作业站字段判定）里有 `raid` / `raid_only` / `normal` / `normal_only`。
实测 **536 个 id 有标志、24 个 `raid_only`**。过滤落在两处：

| 位置 | 行为 |
|---|---|
| `workspace.candidates_for()` | 目标不是 `#f#` 时**剔掉 `raid_only`**，并在 manifest 里记 `raid_filtered`；跑的时候打印一行 |
| `stage_logic.stage_samples()` | 同样剔除 —— 否则"必要位"是**两种模式混着对齐**出来的（实测 SR-EX-4 的 7/7 就是混出来的） |

标题里的「突袭/磨难」只用来**标注**（`raid_suspect()`），不用来过滤 —— 关键词会有假阳性
（例如「非突袭」「普突」这种写法），过滤必须靠数据。

**影响面（实测）**：池子里含 `raid_only` 的关只有 **4 个**
（SR-EX-4 / SR-EX-7 / SR-EX-8 / GA-EX-2），其中 **1 个被选成了 AI 根节点**（SR-EX-4）。
4 关全部重生成后，根节点都换成了普通模式作业（`raid_only=False` 已验证）。

> ⚠️ 这条也回过头影响旧结论：**GA-EX-2 早先分析用的池子里混着 6 份突袭作业**（`21208` 即其一）。
> 涉及 GA-EX-2 的判据（如 `_axis_check.py` 的 5/5）如果用的是混合池，需要按普通池重跑一遍才算干净。

**同一批发现的第二个小问题**：`棋子`（望的召唤物）这类**非干员名**在 `opers`/`actions` 里出现时，
会被匹配引擎当成"缺 1 人"（SR-EX-4 的 `partial 缺1: 棋子`）。这是**同一类虚假信号**
（与 `车`/`快活` 同族）：判断"缺人"前应先排除非干员名。

## 十二、坐标系（2026-09-16 定案：**别再用 `M[H-1-y]`**）

**症状**：编辑器里干员飘在虚空里、整张图看起来"位置很神奇"。
**根因**：同一份数据被翻了两次、又被翻了一次 ——
| 要素 | 取哪一行 | 画在屏幕第几行 | 净效果 |
|---|---|---|---|
| 地图格 | `M[H-1-y]` | `H-1-y` | 两次翻转抵消 ⇒ **地图是对的** |
| 干员/出怪口/门/路径/装置 | 坐标原样 | `H-1-y` | 只翻一次 ⇒ **相对地图上下镜像** |

**定案证据（三条独立）**：
1. **MAA `Arknights-Tile-Pos`（作业坐标的权威空间）与关卡 `mapData.map` 逐格同序 100%**
   （4/5 关；第 5 关地图对称无法区分。反向读法只有 37~74%）。
2. **按 `M[y][x]` 读**：33 关 v1_ai 的 215 个部署 **0 虚空、0 越界**；按 `M[H-1-y]` 读有 **30 个落在虚空**。
3. **职业与格子类型自洽**：SR-EX-3 的艾雅法拉（法师）在 `M[y][x]` 下落在 `tile_replace_wall`（**RANGED 高台**），
   在旧读法下落在 `tile_forbidden`。浏览器实测：旧读法下它**确实压在一格灰色（forb）上**。

**`routes[].row` 与 `map` 的行序相反**（同一份文件里的两种约定）：按 `H-1-row` 换算后，
端点落在 MAA `isStart/isEnd` 上是 **99%（334/338）**，不换算只有 13% ⇒ 在 `level()` 里换算**一次**。

**变更**：`level()` 的 `key/bt` 用 `M[y][x]`；页面 JS 去掉全部 `(D.H-1-y)` 屏幕映射（8 处）；
`_axis_check.py` 的硬编码路线起点同步更新（老坐标会 `StopIteration`）。

⚠️ **推翻一条旧结论**：早先"行原点 `M[H-1-y]` 在 30 关里 28 关胜出、别再翻"是**错的**。
那个指标（近战落点是否落在路径格上）**对上下镜像不敏感** —— 路径与落点**一起**镜像，且多数关的进攻路线是
**竖向**的，镜像后仍在同一批列上（重测两臂：19%→22%、92%→92%，几乎不变）。**它根本回答不了朝向问题。**

| # | 判据 | 结果 |
|---|---|---|
| ① | MAA Tile-Pos 逐格 100% | **100%**（5 关实测；已在代码路径里断言） |
| ② | 33 关 v1_ai 部署 0 虚空 / 0 越界 | **0 / 0**（唯一 1 例是池子里的坏作业，见下） |

> `loadEdits()` 恢复了。清掉 localStorage 后为 **0 处** —— 机制按设计工作，但**测试会被自己的旧编辑污染**。

### 顺带修掉三个下游 bug（都是坐标修正后暴露的）

1. **`waves[].start` 拿到泄漏的旧变量**：我把 waves 的起终点改成换算后的 `st`，但 `append` 里还写着
   `sp.get("col")` —— Python 函数作用域让 `sp` 从上面 routes 循环**泄漏**下来，于是每条 wave 的起点
   都变成最后一条 route 的起点 ⇒ `_arrival_at` 全部返回 None（**时间窗集体消失**）。

   （'上' 会画错射程）⇒ 加 `norm_dir()` 统一成英文枚举（`normalize_job` 与 `stage_logic` 聚合都过一遍）。
3. **`stage_logic` 把 direction 存成元组**（`most_common(1)[0]` 少了 `[0]`）⇒ JSON 里是 `["右", 3]`。
4. 另：`_axis_check.py` 的 ★打装置标记**没排医疗**（判据里排了，明细里没排）⇒ 自相矛盾，已统一。

## 十三、敌人路径（2026-09-16 定案：**按 checkpoints 走，含停留**）

**旧实现**：4 邻域 BFS 最短路径，start→end 直连，**完全没读 `checkpoints` / `allowDiagonalMove` / `motionMode`**。

**数据里其实什么都有**（全 852 条路线扫描）：

| 字段 | 实测 | 含义 |
|---|---|---|
| `checkpoints[].type` | `MOVE` 2648 / **`WAIT_FOR_SECONDS` 637** / `APPEAR_AT_POS` 106 / `DISAPPEAR` 106 | 途经点 / **停留（罚站）** / 换位出现 / 离场 |
| `checkpoints[].time` | 最长 **240s**（4 分钟） | 停留秒数；涉及 **35 关** |
| `checkpoints[].reachOffset`/`reachDistance` | 0.0 / 0.0 | 到达半径（本库未启用） |
| `motionMode` | `WALK` 783 / `FLY` 18 / `E_NUM` 51（占位空路线） | 走路 / 飞行 / 空 |
| `allowDiagonalMove` | **true × 852（全部）** | 敌人真的斜着走 ⇒ 4 邻域 BFS **高估**路径长度 |

**修法**：`level()` 里按 `[起点] + MOVE 途经点… + [终点]` 逐段 BFS（**8 邻域**），飞行用 `motionMode=='FLY'`
判（不再靠"BFS 失败"间接猜）；**到门时刻 = 出怪 + 步数/移速 + 停留秒数**；停留点画 `⏸Ns`（地图 + 时间轴）。

⚠️ **`WAIT_FOR_SECONDS` 的 `position` 不可信**：626 处里 **624 处是 (0,0)**。停留发生在
**链里上一个途经点**（序列：`MOVE(5,9) → WAIT 12s → MOVE(5,6)` ⇒ 在 (5,9) 等）。按 position 画会把 ⏸ 画到角落。

**影响（实测 23 关）：到门时刻平均低估 25.5 秒、最大 150 秒**（act16side_03 的 T+18.33 实际是 **T+158.33**）。
方向是**低估到门时刻 ⇒ 判漏偏悲观**（把"其实来得及"的判成漏）—— 与"不计先锋产费"同一个方向的保守，不会虚假乐观。

| 右路 精锐战士 | T+10.27 | **T+10.27**（不变） | 该路无停留 ⇒ **与既有实测对账依然一致** |
