## 0. 速览（给 preflight/TL;DR）

1. 客户端"账号清单"真实存储在设备文件里：`/data/data/<pkg>/shared_prefs/HypergryphSdkPreferences.xml` 的 `USER_CACHE`（JSON 数组，含掩码手机号+token+绝对时间+hgId）`[实测]`。
2. 面板"登录记录"= 该列表的 UI 镜像：**按最后登录降序、最多约 10 条、只能在列表框内滑动**（页面本身不滚）`[实测]`。
3. 记录时间戳 = **本机该账号最近一次"真实登录（重登/切换登录）"的时刻**；单纯恢复已有会话（冷启动/force-stop 重启）**不会**刷新它 `[实测]`。
4. 冷启动序列：黑屏 → 世界观卡片轮播（START @(800,856)）→ 标题页；会话自动续（登录上次账号，无需重登）`[实测]`。
5. 两个现实死态：账号面板 × 关闭 →「登录被取消，请重试」**卡死不自愈**（MAA 无此 OCR 处理）`[实测]`；强更（客户端版本落后）MAA 侧**无任何处理器** `[源码]`。
6. 发车前"客户端是否就绪"6 条判据见 §5；核心 = 版本号 + 目标账号在登录记录内 + 无已知死态 + 当前 UID 基线。

### 2.2 会话续期与"重登"语义 `[实测]`

- 冷启动 → 直接恢复**上次会话账号**（本次 134****5276），无需重登；`force-stop` 后重启依旧续用 `[实测]`。
- **记录时间戳只在"真实登录"时刷新**：本轮 21:23 我冷启动续用 134 的既有会话，记录时间戳保持在 21:19（另一次真实登录所致），面板显示与字段一致。
  → 推论（已与 19:35 idx14/192、19:40 idx13/187 等跨实例样本互证）：`lastLoginTime` = 该账号在**本机**最近一次真实重登/切换登录时刻；MAA 切号、手动"登录"会刷新；单纯 resume 不会。**每实例独立**（idx11 的 192 记录停在 2025/10/17，而 idx14 的 192 = 当日 19:35）。
- 用途：可据此复盘"某窗口内哪些号真被登过"（配合 docs/MAA_LOG_DICTIONARY.md 的「账号切换 -->>」，两份证据互相对时）。

### 2.3 存储位置与字段 `[实测，只读]`

| 项 | 官服（com.hypergryph.arknights） | JP（com.YoStarJP.Arknights） |

- **隐私红线（必须）**：`token` 为明文凭证、`hgId` 可关联完整手机号 → 任何导出/引用**只保留掩码**（前3+****+后4），本文件及截图均不含明文。读取需 `adb root`（MuMu 可 root；已完成即 release，不影响实例）。
- 该列表**不是**自动切号的开关：MAA 按注入的 `account_name` 掩码在列表里找行并点「登录」；**找不到 → 静默跑当前号**（历史审计结论，机制上对齐：无行可点）。
- **卸载/清数据影响** `[推断]`：shared_prefs 连同 USER_CACHE 被清 → 登录记录空/极少 → MAA 切号必失败（静默）；恢复 = 每号人工登录一次重建记录。旁证：本日 04:4x 观测到某实例仅 2 条记录时，其余掩码号不可切；同日"MAA 切号失败但任务照跑"案例与"列表缺失"现象一致。（不能实测，故标注推断。）

### 2.4 死态：关闭账号面板 →「登录被取消，请重试」 `[实测]`（截图 10）

- 触发：在账号管理面板点 × (1062,250)。复现 1 次。
- 表现：居中弹「**登录被取消，请重试**」（文字区 ~(655–946, 397–434)），**>15s 不消失、像素静止**（620,529B 恒定），无自动重试动画。
- MAA 侧：**无任何处理器**（tasks.json 无「取消/重试/登录被取消」OCR 文本）`[源码]`；若运行中出现，StartUp 重试耗尽的典型失败形态。
- 恢复（已验证）：`am force-stop` + 重新 `am start` → 卡片页 → START → 标题页（会话仍续）`[实测]`。
- 备注：t_65944d5b 的 `tools/client_state_check.py` 已把该状态列入挡路界面清单，preflight 可直接复用其检测。

## 4. 版本与更新

- 版本号可见于：U8 覆盖层左上「Ver:2.7.71」（卡片/启动阶段）、标题页右下「Ver:2.7.71」。系统侧核对：`dumpsys package com.hypergryph.arknights | grep versionName` = **2.7.71 (versionCode=190)**；`playerprefs.LAST_BUNDLE_VERSION=2.7.71`（三方互证）`[实测]`。
- 更新三层 `[实测+源码]`：
  1. U8 启动器层（卡片页覆盖层：清除缓存/网络检测 + Ver 显示）——无自动化处理，勿动。
  2. 资源层：`GameStartCheckResourceOCR`（检查完整性）、`GameStartUpdateOCR`（释放神经递质，MB 进度）——**#self 循环等待**，正常长下载不判失败。
  3. **强更**（客户端版本低于服务器要求）——**MAA 任务面没有任何对应识别**（StartUpThemes 全链无"更新/版本"OCR）`[源码]` → 无法自救；形态会是 StartUp 阶段反复重试直至失败（与历史"卡公告页 50 连败"同类告警）。处置：**人工更包后恢复排班**`[推断]`。
- 对排班影响与预防：强更日常见于大版本日 → 发车前 preflight 必须比对 `versionName`/`LAST_BUNDLE_VERSION` = 预期值（当前 2.7.71）；不等即该实例**不合格**（宁可跳过也不要带着老包发车）。
- 相邻风险（已有文档）：AUTO-MAS 自身更新会触发后端重启吞掉在跑任务（09-27 19:54:14 → v5.4.0，见 docs/MAS_INTERNALS.md）；排班窗口内应避免其自动更新动作。

## 5. 发车前「客户端是否就绪」判据（preflight）

> 全部命令**只读**；`<idx>`=实例号，端口=16384+32×idx（idx≥32 见 docs/MAS_EMULATORS.md 修正公式）；`<pkg>` 官服=com.hypergryph.arknights、B 服=com.hypergryph.arknights.bilibili、日服=com.YoStarJP.Arknights（台/韩未采样）。

| # | 判据 | 命令（远端 adb 或经 MAA adb） | 合格标准 | 处置 |
|---|---|---|---|---|
| S1 | 实例/系统活 | `adb connect 127.0.0.1:<port>` + `getprop sys.boot_completed` | `1`（**不信** MuMuManager/status 假死面） | 重连/重启实例 |
| S2 | 客户端可跑 | `pm list packages \| grep <pkg>`；`dumpsys package <pkg> \| grep versionName` | 存在且 `2.7.71`（=预期） | 不合格：跳过该实例并审计 |
| S3 | 无死态 | 截图 + OCR（复用 `tools/client_state_check.py`） | 非「登录被取消/请重试」「删除确认」「退出确认」等黑名单；非纯黑 >60s | `am force-stop` + `am start` 复位；连续复现→跳过+报障 |
| S4 | 切号可行性 | `adb root; grep` `USER_CACHE`（掩码比对目标账号） | 目标掩码 ∈ 登录记录 | 缺失=切号将静默失败：先人工登录一次该号重建记录 |
| S5 | 身份基线 | `playerprefs.u8sdk_cached_uid` / 标题页 ID vs 身份台账 | 与台账预期一致（防串号） | 不一致=先定位，勿直接发车 |
| S6 | 版本一致 | S2 的 versionName + `LAST_BUNDLE_VERSION` | 两者都=预期（2.7.71） | 强更日人工更包 |

**取证技巧**：`dumpsys usagestats | grep ACTIVITY_` 可查某实例游戏最近 N 次启动/停止时间轴——判定"是否被其他 agent/人工并发占用"、复盘哪段窗口客户端真在跑（本轮就用它区分出了 21:11/21:17 的第三方探测会话与自己的 21:23 会话）`[实测]`。

**节律参考**：冷启动到标题页 30–60s（含卡片）；force-stop 复位 ~2s + 重启 ~35s。
