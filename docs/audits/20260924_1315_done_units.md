## 6. 建议

1. **不要把那 24 个"有凭据"的单位再改回 done** —— 它们已经在 todo，重验一次只花导航不花理智，
   而且**修正 ROI 之后**的重验有机会翻出"当年被坏 ROI 判成 ⊘ 的漏矿"（这正是 CV-EX-8 的剧本：它是那次回滚名单里的一员，随后被扫出徽章并打掉）。
   代价 ~5-6 分钟，收益上限是"一颗源石"。**不对称，所以宁可多验。**
2. `reverify_list.json` 现在带**每条的凭据原文**，汇报时请按档说（`no_evidence` / `suspect_broken_roi` 才是"要查"的，
   `proven_*` 只是"顺带重验"）—— 否则 45 这个数字会被误读成"45 个矿"。
3. 基线/夹具按 **md5**（我上一份报告 §7 的发现）这件事，同样适用于本文件引用的 `map_panels.json`
   （它**没有 `scanned_at`**，我只好用文件 mtime；有 TTL 的 `panels_*.json` 反而更规范）。
4. `scan_map_panels.py` 的这次 NameError 说明：**"补丁脚本"这条路本身有风险**（补丁没落地、且没有自测）。
   建议给这类"给工具打补丁"的脚本加一条"改完立刻 `py_compile` + 干跑一次"的自检（我这次就是这么发现的）。
