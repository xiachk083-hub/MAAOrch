## 1. 【最严重】服务端徽章 ROI 写反 ⇒ `reward_primes` 恒假阴性（假 ⊘ 漏矿）

`tools/maaorch_service.py::panel()` 旧代码：

```python
roi2 = cv2.cvtColor(img[620:1280 if img.shape[0] > 1280 else img.shape[0] - 1, 430:860], ...)
```

正确口径（`main_nav.REWARD_ROI`）是 **y 430:620 / x 860:1280** —— 旧代码把 **x/y 写反**，实际量的是
画面**左下角**（y620-719、x430-860），那里根本没有报酬区。

| 截图 | 正确 ROI（main_nav） | 旧服务 ROI | 徽章最佳匹配位置 |
|---|---|---|---|
| `runtime/_verify.png`（EA-1 面板，徽章**确实在**，下方印「三星获得」） | **0.999 → 有徽章** | 0.644 → 无徽章 | (1001, 532) ← **不在**服务 ROI 内 |

后果：`/panel`、`/all` 的 `reward_primes` 在真面板上是**假**，而 `event_sweep` 的放行条件里有
`reward_primes===true` ⇒ 只能靠 `stars===0` 兜底；一旦星星读数不为 0（见 §2）就直接判 ⊘。
`event_sweep_act41side_20260924_1010.md` 那条 **`⊘ 报酬无源石（分 0.644；0 星）⇒ 不打`** 就是这个 bug
——那天 EA-1 明明有矿（0 星 + 徽章 + 开始行动 −9）。

**修复**：`panel()` 变薄壳，唯一判据搬到 `tools/panel_gate.py::read_panel()`（`stars_calibrated()` +
`main_nav.reward_has_prime()`），服务里那份重复实现**整段删除**。

## 2. 【最严重】`stars` 两套口径差 3 倍 ⇒ 既能假报"三星到手"，也能造成假 ⊘

| 实现 | 公式 | 3 星面板（蓝像素 4400） | 0 星面板 |
|---|---|---|---|
| `main_nav.stars_from_panel`（正确） | `0 if n<300 else min(3, round(n/1470))` | **3** | 0 |
| 旧服务 `panel()` | `round(n/490)`，无上限 | **9** | 0 |

实测：`runtime/_map_now.png`（EA 地图）旧服务报 **3 星**、正确口径报 1、肉眼是 **0 星面板**；
`runtime/_mt3.png`/`_trp.png`/`_pvex4res.png`/`_ep8_chk.png`（3 星面板）旧服务都会报 **9**。

两条真实伤害：
1. `event_sweep` 的复核 `stars2 >= 3 ⇒ rec.action='done'（源石到手）` + `recordOutcome(..., 3, 'panel-verified')`
   ⇒ 1 星关也能被判成"源石到手"，并把**假 3 星写进 P(3★) 账本**（污染排产）。
2. 反过来：一条 1 星关在旧服务里读成 3 ⇒ `stars===0` 不成立 ⇒ 失去唯一有效的兜底 ⇒ 判 ⊘ 漏矿。

**修复**：`stars` 统一走 `main_nav` 标定口径（封顶 3、<300 记 0），且**页面不是「关卡详情」时
`stars/cleared/reward_primes` 一律 `null`**（低置信读数不许判 done/⊘）。

## 3. 【最严重】结算页/2★ 结论被丢掉 ⇒ 花了理智什么都没记 + 下一轮又从头再来

`event_sweep` 的复核段依赖 `/panel` 的 `text`（判"屏上是不是结算页"）和 `cleared` 字段，
而**服务端 `/panel` 从来不返回这两个字段**（只有 spawn `panel_gate.py` 的老路才返回）。
只要常驻服务在跑（它就在跑），这段逻辑就整体失效：

- `g1?.text` 恒 undefined ⇒ **结算页从不被点掉** ⇒ 下一轮导航必然失败 ⇒ 队列再跑一遍（又是"从头再来"）；
- `g2?.cleared` 恒 undefined ⇒ **2★ 从不写 `partial`**。

10:15 那次真实跑（`node tools/event_sweep.mjs --event act41side --prefix EA --only EA-1 --wants 普通
--apply --sanity-min 9 --max-tries 3`）的证据链：

```
sweep_reports/act41side_01__普通.json : 3 份轴全 verdict=done（"打完，待核三星"）但总体 result="未成功"
runtime/reports/event_sweep_act41side_20260924_1015.md : | EA-1 | 普通 | ❌ run | 未成功 |
runtime/_refill.png / _after_skip.png : EA-1「行动结束」结算页，**亮 2 颗蓝六边形 = 2★**
```

即：**真打完了（2★）、花了 9 理智、账本里既没有 done 也没有 partial，只有"未成功"**，
队列的 `classify` 于是判 `notdone` 再重试 ⇒ 每轮再烧 9 理智。这正是"假阴性造成重复浪费"的闭环。

**修复（判据层，我落）**：`read_panel()` 现在返回 `cleared`（=stars>0，低置信 null）、
`stars_conf`、`page/page_score/page_margin`、`result_stars/result_lit/result_blue/result_conf`，
并给 `/panel`、`/all` 加 `?text=1` 可选 OCR 文本。
**调用侧（`event_sweep.mjs`，fixer-1 的 task-3）需要**：① 结算页判定改用 `page=='结算页'`
（实测 `_refill.png` = 结算页 0.982 / margin 0.387，比 OCR 更快更准）；② `result_stars` 定
done(≥3)/partial(1-2)/failed(0)；③ **`result_stars==null` 时绝不用面板 `stars` 冒充结算读数**；
④ `cleared===null` 要显式处理，别掉进最后的 `done` 分支。接口已与 fixer-1 对齐（他离线自测 10/10 通过）。

## 4. 【已修】`_prime_queue3.py`：死变量、不可达代码、`noreach` 永久冻死 85/195 个单位

1. `renav_fails` 自增后立刻 `break`，**从没被读过**；紧随其后的 `time.sleep(5)`/`continue` 永不可达。
2. `classify()` 靠中文子串猜结局：`"不在活动图里" in out`，而服务端措辞是「**不在活动地图上**」、
   `mt_nav` 是「5 轮内没能进到…」⇒ 只要任何一个工具改一个字，分类就**静默失效**。
3. **`noreach` 一旦写下就永久跳过**（`if st.get(key) in ("done","noreach"): continue`），
   而实测状态文件里 **195 个单位有 85 个是 noreach** —— 包括 **EP-EX-1..8 突袭、PV-EX-1..8 突袭、
   LE 全家突袭**，恰好都是"一颗源石"的高价值矿。批量来源是 02:52–03:00 的
   `放弃本次进 <活动>（连进两次失败），该活动的单位标 noreach`（一次把整章标死）。
4. 理智不足时空等 `sleep(240) × 最多 40 轮` = 单关最坏**干等 2.7 小时**，而"等"根本不解决问题。

**已修**：删死变量与不可达行；分类改为**先读 sweep 写的账本 JSONL**（结构化，字符串匹配只作兜底，
并补上「不在活动地图上」「读数不可信」两种措辞）；`noreach` 加**冷却账本**
`runtime/_prime_noreach.json` + **6h TTL** + `--retry-noreach`（旧 noreach 无记录 ⇒ 一律视为过期，
本轮重验）；理智等待封顶 `--max-waits`（默认 3 轮 = 12 分钟）后记 `wait` 换下一关。
自测：`classify` 9/9；`--dry` 输出 **「还待打 147 个；其中 noreach 会被重试 85 个」**。
