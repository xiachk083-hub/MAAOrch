# task-18 审计：排产改「每点理智的期望源石」是否合理 · 2026-09-24 14:00

审计人：**auditor-1**｜离线（真实数据：`mine_plan.json` 339 行 + `_stage_table.json` 的 ap + 状态表）
工具：`runtime/_audit_task18_sched.py`（四种排法对照 + 到线天数模拟，可复跑）

## 0. 结论摘要

1. **Lead 这版（B）比旧版（A）确实更好，但"达标天数接近翻倍"不成立** —— 实测量级是 **12 天 → 11 天（≈8%）**，
   纯本关效率（C）也只有 **10 天**。原因见 §2：便宜关只有 96/502 个单位，**大头（134/157 EV）在主线数字章（理智 18~25）**，
   前段加速能省的天数有硬上限。
2. **没有饿死大章节**：B 让主线 **ch9 从第 75 名提前到第 28 名**；PV/EP/LE/MT 排到 #341+ 是因为**它们剩余 EV ≈ 0（矿已挖完）**，不是被饿死（见 §3 表）。
3. **`ap` 兜底是未来的陷阱，已修**：实测当前 0 个单位缺 ap，但旧写法 `max(1.0, ap or 1)` 一旦遇到缺字段的学习产物，
   会把它当 1 理智 ⇒ 效率虚高 20 倍 **顶到队首**，且 `--sanity-min` 同时变成 1（必失败）⇒ 现在按 `AP_UNKNOWN=21` 保守兜底 + 警告。
4. **顺手补上一条真正有用的**：面板预扫扫出「徽章仍在」的关**插到最前**（`ev` 是历史推测，徽章是当前实测）。
   复跑 `--dry` 立刻见效：**`CV-EX-8|突袭` 排到第 2**（普通 11:42 已拿，突袭没打过 ⇒ 突袭面板有独立首通源石）——**可能是一颗现成的矿**。

## 1. ① 公式是否合理（用真实数据量化）

四种 key（同一批 502 个单位、同一份 EV/ap）：

| 排法 | 定义 | 到线天数（缺 66 颗） |
|---|---|---|
| A 旧 | `(-章EV, -本关EV)` | **12 天** |
| B 本次改动 | `(-(章EV+本关EV)/ap, -章EV, ap, code)` | **11 天** ✅ |
| C 纯本关效率 | `(-本关EV/ap, -章EV, ap, code)` | **10 天** |
| D 章归一 | `(-章EV/章内理智中位, -本关EV/ap, …)` | **12 天**（≈A） |

敏感性（"回滚 todo 里其实没矿"的比例）：0% → A12/B11/C10/D12；30% → 12/11/11/12；50% → 12/11/**12**/12。
⇒ **B 稳、C 在噪声里**（C 只快 1 天，且在 50% 假 todo 时退化到 12 天）⇒ **建议保留 B，不要为 1 天去换成 C**；
B 还额外有"同章连打、少进活动"的操作好处。

**为什么不是 2 倍**（这是本次审计最该被记住的一条）：
- 单关口径确实是 2.1 倍（10 理智 → 0.05 颗/理智 vs 21 理智 → 0.0238）；
- 但**便宜关（ap 9~12）只有 96/502 个单位**，且它们的 EV 占比更小；把这段做完之后，速率立刻掉回主线水平；
- **EV 的 85% 在主线数字章**：章13 19.0、章14 18.0、章9 17.0、章12 17.0、章7 16.0、章11 16.0、章8 16.0、章10 15.0 = **134 颗**；
  活动全部加起来只有 23.3 颗（AD 11.5 + CV 11.5 + PV 0.3，EA 的 11.5 还卡在 noreach）。
⇒ 排产能动的只是"前 10 天的曲线斜率"，动不了总量（跑完全部 todo 都是 30 天/157 颗）。

## 3. ② 饿死定量：各章第一个单位出现在第几名

| 排法 | 章首名次（前 8） |
|---|---|
| A 旧 | **13:#1**、14:#39、9:#75、12:#103、7:#143、11:#169、10:#207、8:#309（CV #237、AD #261、EA #285） |
| **B 新** | CV:#1、AD:#4、EA:#6、**9:#28**、13:#56、7:#84、14:#110、12:#136、11:#202、10:#242、8:#288 |
| C | CV:#1、AD:#4、EA:#6、9:#50、7:#78、8:#104、13:#142、14:#170、12:#196、11:#228、10:#258 |
| D | **9:#1**、13:#35、7:#73、14:#105、12:#141、CV:#175、AD:#199、EA:#223 |

- **结论：没有"饿死"**。B 把主线的入口从 A 的 #75 提前到 **#28**；唯一被推后的是**章13（#1 → #56）**，
  而原因是它最贵（21 理智）而 EV 只有 19 —— 按效率排本来就该让便宜关先走。
- **PV/EP/LE/MT 排到 #341~#384 不是饿死**：它们的 `chapter_ev` 分别是 0.3 / 0 / 0 / 0（矿早挖完了），
  8/8/7/15 个"待打"条目是**重验回滚**或 ev=0 的空壳 ⇒ 排在后面是对的。
- D（"先章内 EV/ap、再跨章 EV/中位ap"）**不比 A 好**（12 天、前 20 全是章9）—— 因为各章理智中位数（15~21）差得不多，
  而章 EV 差得多 ⇒ 归一化后还是"章块"排序。**所以"章归一"这条不改**。

## 4. ③ 极端情况 `ap=0/None`

- **实测：0 个**（`ap` 分布：9×17、10×62、12×17、15×71、18×87、20×36、21×164、24×44、25×4）。
- 但**旧兜底是真陷阱**：`max(1.0, ap or 1)` 会把缺字段单位当 1 理智 ⇒ `eff` 虚高约 20 倍 ⇒ 顶到队首；
  同时 `sweep()` 传的是 `--sanity-min str(u["ap"])` ⇒ 理智门槛变成 **1**，会在只剩 1 点理智时硬开（必失败/卡住）。
- **已修**：新增 `AP_UNKNOWN = 21.0`（最贵档，保守方向），缺 ap 时按它排 + 打警告（本轮 `--dry` 无警告 ⇒ 当前没有这种单位）。

## 5. ⑤ 我改的两处代码（`runtime/_prime_queue3.py`）

1. **`ap` 兜底**：`ap = float(u.get("ap") or 0); ap = ap if ap > 0 else AP_UNKNOWN`，并在有缺字段时 log 警告。
2. **预扫的矿插到最前**（`tier = 0 if 代号 in panel_mine else 1`）：
   读 `runtime/learned/panels_*.json` + `runtime/reports/map_panels.json` 里 `reward_primes is True` 的关
   （**只读缓存，不碰模拟器**）。理由：`ev` 是历史推测的 P(3星)，而"徽章仍在"是**当前实测的确定矿**，
   一颗确定的矿不该排在 20 个推测的后面。**安全性**：即使缓存的 `mine` 过期了，横扫的闸门在真打前还会再读一次面板
   （无徽章 ⇒ ⊘），所以最坏情况是多一次导航，**不会白花理智**。
3. 顺带把"为什么不是 2 倍"的量测写进注释（免得下次又有人凭直觉改回去）。
4. 回归：`py_compile` 通过；`--dry` 复跑头部为 `CV-EX-8突（tier 0，todo）→ CV-1/2/3 → AD-1/2 → CV-EX-1/2 …`，
   与"便宜优先"的预期一致；`noreach 会被重试 108 个`（我上轮的 TTL 修复仍在生效）。

## 7. 结论与建议

1. **保留 B**（本次改动）—— 比旧版好、无异常项；**不要**换成 C（差距在噪声内）或 D（≈A）。
2. **别把排产当成主要杠杆**：EV 的 85% 在主线，排产只能省 ~1 天；真正的杠杆是
   ①主线可达性（main_nav 能不能稳定进 18~21 理智的关）②主线 P(3★)（轴质量/练度）
   ③把 **noreach（108 个、含 EA 的 11.5 颗）** 救回来（我已加 6h TTL 自动重试）。
3. **`CV-EX-8|突袭` 建议今天就验**（我的新规则把它排到 #2）：普通已拿、突袭未打 ⇒ 突袭面板大概率还有一颗首通源石。
4. 未决：`ap` 缺字段的真实来源只有一个 —— 学习产物（`runtime/learned/stages_*.json`）里的新关没有理智字段；
   现在有保守兜底，但**更好的做法是让它带上 ap**（`discover_stages` 顺手从面板「开始行动 −N」读出来）。
