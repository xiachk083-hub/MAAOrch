# 自动重新入队生命周期 — 方案（待拍板）

> 用户方向（2026-08-10 确认）：「队伍健康时 MAA 退出应该重试任务，不能当刷完」。
> 完成判定用 MAA 的 AllTasksCompleted（非 exit_code）；失败/中断自动重入；
> 停止 = 做完 + 体力 ≤30%。现状：完成不重入 ✓、停止阈值 30% ✓、
> 失败自动重启 3 次后挂起（与"失败自动重入"方向有差距）。

## 现状盘点

| 路径 | 现状 | 目标 |
|---|---|---|
| 任务完成（AllTasksCompleted） | 收尾出队，不重入 | 不变 ✓ |
| 刷关空转（Fight 0 把） | 今晚已修：判 -13 重试 | 不变 ✓ |
| 失败（exit≠0 且未完成） | 自动重启，**3 次后挂起** | 自动重入（挂起只留给环境问题） |
| 停止（做完+体力≤30%） | 收尾出队 | 不变 ✓ |
| 环境问题（模拟器起不来/失联） | 3 次后挂起 | 挂起保留（否则无限重试风暴） |

## 核心问题：怎么区分"任务失败"与"环境问题"

现状把两类混在一起都用 3 次上限。要改的判定逻辑：

```
失败后检查 → 分类：
├─ 环境问题（模拟器进程不在 / ADB 失联 / MAA 启动即崩 / ErrorCongratulations）
│   → 维持 3 次上限 → 挂起（避免今晚这种重试风暴）
└─ 任务失败（MAA 正常运行但任务链报错 / 未完成退出 rc≠0 / 关卡导航失败）
    → 自动重入（不消耗环境挂起次数），连续任务失败仍累加 _err_count
      （有启动宽限保护的错误阈值会兜底）
```

## 改动点

1. `runner._cleanup` 的自动重启分支：按 `exit_code` + 失联标记 + 启动窗口
   结果分类——环境类才走 `_auto_restart_count`（3 次挂起），任务类直接
   `launch_queue.enqueue(aid, "retry", priority=0, slot=原slot)` 重入
2. 重入需要 slot 语义保留（queue.json 已落盘 slot ✓ 今晚修过）
3. 任务失败重入加节流：同一账号 1 小时内任务失败重入 ≥5 次 → 升级为挂起
   （防止"关卡永远导航失败"型无限重入，保险丝）

## 风险

- 分类判定错了方向 → 环境问题无限重试（今晚风暴重现）或任务失败被挂起。
  缓解：分类只用硬信号（模拟器进程/ADB/MAA 启动成功与否），不猜。

## 验证

1. 本地单测分类函数（构造 exit_code + 失联标记组合）
2. 生产观察：挑 1-2 个账号制造任务失败（如关卡导航失败）看是否自动重入不挂起
