## 已确定事实

### 1. 几何 / 地图理解

* 已能读取 Roguelike 地图与路线数据。
* 已覆盖 23 张地图 / 777 条路线。
* 已能计算敌人沿路线的到达时间、路线占用、交通负载。
* 已完成道路图、blockable cell、vertex-splitting、max-flow/min-cut。
* 已区分 `FINITE(k)` 与 `INF_NO_BLOCKABLE_ROUTE`。
* 已有 `unblockable_route_ratio`、`cut_frequency`、`cut_impact`、`traffic_load`。

### 2. 几何目前的真实状态

我们已经撤回此前“133 px vs 147 px / 约 10% 缩放误差”的结论。

当前不能证明全图存在固定 0.9 scale。

* synthetic fitting：✓
* synthetic one-to-one matching：✓
* 真帧 component-level matching：⚠️（当前真帧有效对应仅约 23–29 对，残差约 44–71 px，homography 在真帧上出现退化解）
* 因此目前对 similarity / homography **不做裁决**。

当前下一步是：

> **只在绿色高亮区域内部提取格缝 / 格边，建立 tile-level correspondence，而不是继续让整张图的角点互相抢。**

另外，我们也记录了一次**方法学失败**：曾用“最大的蓝色连通块”当防守点锚，结果两张不同的图报出同一个坐标 (450,468)——
那是固定位置的蓝色 UI 元素 ✗ ⇒ 该批读数全部作废。目前唯一有效的一组锚点数据是三帧**人工核对过**的：
防守点标记 ↔ 预测格心 = **52 / 65 / 67 px**，除以各图投影格距（约 120~160 px）⇒ **≈0.35~0.55 格**。

### 3. “部署容差”已经有硬证据

我们的执行安全闸是：`FALLBACK / UNKNOWN → 不部署`。实际测试中，部署位置容差约为**半格**。

这意味着我们现在最关心的并不一定是“能不能把全图每一个格子的投影都做到像素级精确”，而是：

> **对于真正要部署人的 2～3 个候选格 + 防守点，局部几何是否已经足够可靠？**

这是本次求助希望优先确认的问题之一。

### 4. 单格面积已经出现一个可靠的几何先验

在真帧中，以“区域内绿通道中位 +8”阈值切出来的候选块面积：**10861 / 10502 / 9945 px²**，
而 TileCalc2 预测单格面积约 **10818 px²** —— 数量级是吻合的。

但目前的**筛选逻辑还没有写对**，所以这只能作为候选先验，不能直接宣布“已经能切格”。

### 5. 策略闭环目前是最大的空白

现在已有 `observe → 地图/路线理解 → 候选位置计算 → 动作执行`，以及基础执行回放（`observe_job` 逐动作记录、`battle_loop.py`）。

但真正缺的东西是：**系统主动改变一版策略**。目前还没有真正发生过：

```text
策略 A → 实战失败 → 分析失败原因 → 修改规则 / 参数 → 策略 B → 再执行
```

因此目前**规则库基本为空**。

### 6. 战斗数据侧与视觉侧能力不对称

数据侧已经能够计算：某时刻、某条路线、第几格存在敌人 / 敌人预计到达时间。
画面侧目前：**还不能稳定识别具体敌人**（ONNX 现有 `deploy_direction_cls` / `operators_det` / `skill_ready_cls`），
但**已经能做敌人总数 OCR**。

因此我们存在一个候选架构：

```text
数据模型：敌人是谁 / 从哪里来 / 什么时候到哪里
        +
画面：只确认“实际画面是否符合模型预期”
        ↓
一致性校验
```

而不是立即投入敌人检测 / 分类。我们希望确认这种架构是否足以支撑第一版独立推关。

## 具体问题

## A. 几何到底需要精确到什么程度？

这是我们认为**可能最省力、应该优先回答的问题**。我们当前安全闸已明确 `FALLBACK / UNKNOWN → 不部署`，并且实测部署容差约半格。

### A1

**“全图格网精确”是否是独立推关的必要条件？** 还是第一版实际上只需要：

```text
地图整体：粗略 / 可解释
真正执行：要放人的 2～3 个格 + 防守点 + 必要的路径 / 敌人位置 → 局部达到可靠精度
```

如果后者成立，我们希望直接绕开“全局几何裁决”。

### A2

如果你认为必须做全局几何裁决：当前 A-2c 已经卡在“无法可靠切出 tile”，而单格面积先验已经比较吻合。请在以下路径中直接给优先级：

1. 利用预测单格面积量级作为先验继续切格
2. 只在绿色高亮内部做 watershed
3. 换一种锚点 / 几何证据
4. 其他你认为更快、更可靠的方法

请不要只给算法名称，最好说明：**为什么它比其他路径更适合我们当前的数据和失败模式。**

## B. 策略 / 轴生成：最小闭环应该长什么样？

这是目前我们最缺、也最不知道应该从哪里开始的一块。目前 `观察 ✓ / 地图路线 ✓ / 候选位置 ✓ / 执行 ✓`，但 `策略生成 / 失败归因 / 策略修改 / 规则积累` 基本为空。

### B1

第一版“策略”应该是什么粒度？例如：

```text
条件 → 选择防守轴 → 选择干员 → 选择位置 → 选择技能时机
```

还是应该先限制成更小的规则：

```text
如果路线 A 负载高 → 优先封 A
如果某点同时覆盖两条路线 → 优先考虑该点
如果上一局在 T 秒附近漏怪 → 下一局提前部署 / 换位置
```

### B2

我们已经有 `observe_job` 的逐动作回放。**怎样从一局失败中提炼第一条可复用规则？** 希望给一个具体例子：

```text
观测 → 失败事件 → 失败归因 → 参数 / 规则变化 → 下一局验证 → 规则入库
```

### B3

第一版是否应该**先不要做通用规则库，直接做一个极小的可解释策略闭环**？例如只支持：

```text
选择 1 个防守轴 + 指派 2～3 名干员 + 按时间执行 + 观察结果 + 失败后只允许修改一个变量
```

如果你认为这比一开始做“通用策略生成器”更合理，请明确给出原因。

## C. 执行器生产化：`battle_loop.py` 之外还缺什么？

现在 `battle_loop.py` 已经可以跑实验，但还不是生产级执行器。请只列**独立推关第一版真正不可绕过的生产化能力**。例如是否必须有：

```text
动作前条件检查 / 动作后确认 / 超时 / 重试 / 状态机 / 异常中止 / FALLBACK / 动作幂等 / 执行日志 / 回放
```

请区分 **MUST HAVE / SHOULD HAVE / 可以以后再做**。
不要让我们为了“工程完整性”提前做大量暂时不会影响独立推关能力的东西。

## D. 敌人识别到底必须补吗？

当前能力：

```text
数据侧：路线 / 敌人 / 预计到达格 / 预计时间        ✓
画面侧：具体敌人识别                              ✗
画面侧：敌人总数 OCR                              ✓
```

我们考虑第一版先采用：

```text
数据模型预测：敌人应该在哪里
视觉：不负责识别每个敌人，只负责检查 敌人总数 / 关键区域是否异常 / 预测实际是否严重偏离
```

请判断：**这条“数据驱动 + 视觉一致性校验”的路线，能否支撑第一版独立推关？**
如果不能，请指出**真正不可绕过的视觉信息是什么**。

我们尤其不希望因为“最终系统理论上应该有完整敌人检测”而提前投入一个暂时并不影响闭环的模型。

## 最重要的问题：请直接改我们的排序

我们目前自己的最省路径判断是：

```text
① 几何过闸 → ② 指派：格 → 人 → ③ 最小闭环：独立完成一局
```

请你不要默认接受这个顺序。如果根据上述事实，你认为更合理的是：

```text
① 执行器安全闭环 → ② 局部几何 → ③ 一个最小策略 → ④ ...
```

或者：

```text
① 先做一个极小策略闭环 → ② 几何只做到局部可用 → ③ ...
```

**请直接改排序，并说明每一步为什么排在这里，以及它解除的是哪个后续阻塞。**
