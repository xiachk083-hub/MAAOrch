# 打关 Agent（Clear Agent）设计

> 2026-09-15 立项。起因：用户看了 B 站《GPT-6 全自主通关 5-10》（UP: frostofwinter）——
> 作者自述"其实不是全自动，做了很多 engineering"，早期用 Opus/GPT-5.5 **连前几个干员都摆不好**。
> 用户结论："他明显高级，是专门的 Agent"。
>
> 本文把"专门 Agent"该有的结构、我们已有/缺什么、以及落地顺序写清楚，
> 供下次直接开工（今晚的教训在最后一节）。

## 1. 为什么"拼脚本"不行（今晚实证）

| 做法 | 结果 |
|---|---|
| 命令行 MAA 打 + adb 点坐标导航 | 两只手抢同一界面 → 反复选择干员、卡在编队页死循环 |
| 反复 `nohup` 起后台驱动 | 父进程被杀子进程不死 → 堆积 19 个 python 进程 → CPU 拉满 |
| 盲等（sleep 150s） | 失败/结束早已发生，反应慢半拍 |
| 只认 5 个状态 | 编队页/关卡详情页/弹窗都判成 other → 无人处理 → 卡死 |

结论：**必须是单一控制者 + 完整状态机 + 每一步可验证**，这是 Agent 与脚本的分水岭。

## 2. 组件清单：已有 vs 缺

| 能力 | 现状 | 位置 |
|---|---|---|
| 实时状态判别 | ✅ 5 态（战斗/三星/失败/地图/编队） | `tools/screen_state.py`（模板匹配 ~50ms/帧，自检 5/5） |
| 世界模型（地图/波次/敌我数值） | ✅ | `tools/stage_value.py`、`tools/ga_batch_value.py`、`data/_level_*.json`、`data/_enemy_db.json` |
| 打法生成（站位/朝向/分工） | ✅ | `tools/derive_plan.py`（17 关 GA 方案在 `data/copilot/ga_derived/`） |
| 感知（截图/OCR/锚点） | ✅ 真机验证过 | `services/ai_agent/percept.py` |
| 战斗内视觉（技能就绪/干员检测） | ✅ 部分（无敌人感知） | `services/ai_agent/battle_vision.py` |
| 执行器（点击→验证→留证→重放） | ✅ | `services/ai_agent/actuator.py` |
| LLM 决策通道 | ✅ `deepseek-v4-pro`（纯文本，本地看图→文字→LLM→落点） | `tools/ai_agent_think.py`、`services/ai_agent/brain.py` |
| **单一控制循环（编排→尝试→判定→分析→改招）** | ⚠️ 只有脚本雏形 | `tools/plan_loop.py`（编排/判定/归因已有，缺状态机兜底） |
| **状态机补全** | ❌ 缺 关卡详情页 / 弹窗 / 理智不足 / 结算 | 待补（有截图可裁模板） |
| **战斗内策略（规则优先，LLM 兜底）** | ❌ 无 | 待建：敌方波次时间表 + 费用表 + 技能就绪 → 规则决策 |

## 3. 目标架构（单一控制者）

```
                  ┌── 世界模型（离线算好）: choke/路线数/敌人数值/我方数值
                  ↓
  编排器 Planner ──→ 方案(copilot json: 谁在哪/朝向/技能)
                  ↓
  控制循环 Loop ──→ 状态机 StateMachine（screen_state 扩全）
                  │        ├ 战斗 → 规则策略(补位/开技能) + LLM 异常兜底
                  │        ├ 失败 → 归因(用时/最后一步/部署失败) → 改招 → 再编排
                  │        ├ 通关 → 三星核验 → 下一关
                  │        └ 中间态(编队页/详情页/弹窗) → 按定位策略推进（单向一步）
                  ↓
  执行器 Actuator（点击→验证→留证→重放）—— 唯一控制者，先停 MAA
```

要点：
1. **编排在前，Agent 在后**：站位/朝向/分工用数值模型离线算（我们的强项，GA-8 靠它一次三星），
   Agent 只负责"看得准、点得准、失败会改"，不负责从零想站位；
2. **规则优先、LLM 兜底**：费用/技能/波次时间表可规则化，LLM 只在规则覆盖不到时才介入；
3. **安全闸**：开跑前确认 MAA 已停（否则拒绝启动）；首轮一律走**演习**（零理智）；
4. **每步留证**：`logs/agent/<会话>/steps.jsonl` + 前后截图（沿用现有执行器）。

## 4. 落地顺序（每步都可验收）

1. **补状态机**（半天）：裁模板补 `detail`（关卡详情页）/`dialog`（通用弹窗）/`noSanity`（理智不足）/
   `result`（结算）；用今天存下的实机帧自检（`data/mastery_scan/*.png` 现成）。
2. **控制循环收口**（半天）：把 `tools/plan_loop.py` 的状态处理改成"跳变才动作 + 超时自愈 +
   先确认无 MAA 进程"，并把"点节点"限定在"从地图进关卡页"这一种转移上。
3. **规则战斗策略**（一天）：读费用/技能就绪（`battle_vision`）+ 敌方波次时间表（`_level_*.json`）
   → 输出"该放谁/该开技能"；LLM 只处理规则外情况。
4. **演习首验**（半天）：EX-2 演习打通（零理智），全程录像/留证，成功后切正式。
5. **闭环**：EX-2~EX-8 逐关跑"编排→尝试→归因→改招"，账本落 `data/plan_loop/<stage>/ledger.json`。

## 6. 参考实现拆解（用户截图：该 UP 的 Agent 控制台，2026-09-15）

从截图能直接读出的结构：

| 面板 | 内容 | 对我们的启示 |
|---|---|---|
| AI Gameplay 观测台 | 左侧实时游戏画面 + 识别出的战场数字（**敌人 16/73**、**费用 29**、剩余可放置角色、干员卡与技能按钮） | 他的 agent **读战场数字**（敌人余量/费用/可部署位）——我们的 `battle_vision` 目前没有敌人/费用读数，要补 |
| Agent 工作台 · 决策输出 | 每轮一条结构化决策（含"该特性仅可用于…不能用常规治疗"这类**推断**） + 「CLICK 69 轮：模拟输出(待执行验证)」 | **按动作逐条决策 + 每条都待执行验证**，不是批处理一把梭 |
| 输入上下文 / 工作记忆 | 「历史教训」「已证明…」「下一步预计…」 | 他把**局内记忆**喂回模型（已证明有效的经验/教训）——这是"越打越准"的来源 |
| 决策时间线 | 行动 / 等待 / 停止 的逐轮时间线 | 一局打了 **69 轮**决策，粒度是"每次点击" |
| CURRENT SESSION | 明日方舟 5-10，2026-09-05，69 轮，运行中 | 单关就是几十轮迭代——慢是常态，**关键是每轮都有效** |

结论（对我们的直接要求）：
1. **战斗内要读数**：敌人余量、费用、可部署位、我方存活/技能就绪 —— 规则决策的输入；
2. **逐动作决策 + 执行验证**：一次一个 CLICK，点完立刻验证（我们执行器已支持）；
3. **局内工作记忆**：把"已证明/已失败"写进上下文（我们可先落成 json，后续再接 LLM）；
4. **不急着一把通关**：几十轮迭代是正常量级，别用盲等去省事。


## 5. 今晚的教训（写进规矩）

- 绝不用 `nohup ... &` 起常驻驱动；要常驻就一个进程、能自证存活、退出时带走子进程；
- 绝不两只手操作同一模拟器：要么 MAA，要么 Agent，二选一；
- 绝不盲等：状态变化驱动（≤1s 反应），失败立刻处理；
- 绝不重复点同一坐标：点节点只在"地图→关卡页"这一种跳变上做一次，其余状态只观察。

## 7. 算轴层（2026-09-16 补，来源：BV1jCYn6gEgP）

用户 2026-09-16 抛来第二个对标参考——B 站《AI已经会算轴和思路优化了，离攻略危机合约还有多远？【单人HS-EX-8突袭】》
（UP: Kelin__，BV1jCYn6gEgP）。**该 UP 的分工是"GPT 只算轴、操作全程是人"**，他本人在评论区两次确认
（"gpt 是算轴和思路优化的，最后还是人操作"；"核心算轴 Canvas"）。过程：PRTS Wiki + 关卡数据 + **失败视频**喂给 GPT
→ 算出 30 套轴（最高通过率 14%）→ 换站位后再喂失败视频 → 得到 189.8s 第 1 帧开技能的轴 → 过。

**核查代码后的结论：我们差的不在执行，全在算轴。**

| 层 | 现状 | 依据 |
|---|---|---|
| 执行（帧级操作） | ✅ **MAA 原生就支持**，是我们没用 | 作业协议 action 有 `ResetStopwatch` + `elapsed_time`(毫秒) + `BulletTime`(1/5 速) + `pre/post_delay`；`skill_usage: 0` 配 `{"type":"Skill"}` 即手动轴 |
| 执行（我们的实际用法） | ❌ 从没碰过 | `data/copilot/ga_derived/` 19 份推导作业**只有 `SkillDaemon`（摆完挂机）**；全仓库 `ResetStopwatch`/`elapsed_time`/`BulletTime` **0 处**，`skill_usage` 只用过 0/1/2 |
| 算轴原料 | ✅ 已有 | `data/_level_*.json` → `waves[].fragments[].actions[]` 每条 SPAWN 带 `preDelay`(秒)/`interval`/`routeIndex` → 可推**每个敌人到达某格的绝对秒数**；`data/_enemy_db.json` 2151 个敌人含 `baseAttackTime`(攻击间隔)/`atk`/`def`/`magicResistance`/`moveSpeed` |
| **轴搜索算法** | ❌ 无 | `derive_plan.py` 只管谁在哪、朝哪，**不含时间维度** |
| **通过率/时序仿真器** | ❌ 无 | 对方有"30 套轴、最高 14%"的口径，我们没有任何东西能估通过率 |
| **战斗过程回喂** | ❌ 无 | `plan_loop.py` 的归因只在 MAA 日志层，没有帧/视频证据进决策 |

两点值得记的旁证：
1. **协议里 `skill_usage: 3 - 自动判断使用时机` 官方标注"（画饼.jpg）"** —— 这个空缺正是算轴层要填的。
2. **MAA 官方 2025-02 已经危机合约登顶过**（`BV1W6Ake4EE2`《危机合约 净罪作战 MAA 登顶！》，80 万播放），
   但简介写的分工是"核心适配 @萨拉托加 / 技术支持 @Alan-Charred"，正文说"**牛也是要凹的**" ——
   即**逐关手工适配 + 反复凹概率**，不是通用求解。这与本 UP"14% 通过率、试几次"是同一件事，
   也再次印证第 5 节"单关几十轮是常态"。

**对第 4 节落地顺序的修订**：原第 3 步"规则战斗策略"升级为**算轴层**，拆成三小步——
(a) 从 `_level_*.json` 的波次 actions 生成"敌人到达时间表"（纯计算，可离线验收）；
(b) 在方案 JSON 里落地第一条**手工轴**（`ResetStopwatch` → `elapsed_time` → `{"type":"Skill"}`），
    在一关演习里验证"按秒开技能"确实生效；
(c) 再谈轴搜索（枚举/启发式）与通过率估计——**先证明执行通道通，再谈算法**。


## 8. 视觉能力实测与分工（2026-09-18，两轮 8 次调用）

**判据：部分可用**（按用户判据表落"部分错"那档）。素材：`data/test_battle.png` / `test_battle_b.png`（GA-EX-2 帧）、
`data/test_battle_pa.png`（日服 PA-1 演习暂停帧）；原始回答与 reasoning 在 `data/_vision_test_result.json` / `data/_vision_pa_result.json`。

| 能力 | 实测 | 备注 |
|---|---|---|
| 读**费用** | ✅ 5/6 | 错的那次把顶部「部署上限 3」读成了费用 |
| 读**卡排张数** | ✅ 6/6 | 三帧全对（8 / 11 / 11） |
| 敌人**总数** | ⚠️ **有敌人时 4/4；空场必幻视** | 真值 0 敌人那帧，三次答成 4 / 4 / 1 |
| 敌人**位置**（左中右） | ❌ | 同一帧三次给出三种分法 ⇒ 纯噪声 |
| **我方干员** | ❌ 被遮挡就看不见 | 不加提示两次答 0；**提示"蓝绿血条+橙色朝向箭头"后立刻答对** |
| 单帧延迟 | 6.1 / 18.8 / 31.8 / 64.6 / 69.2 s | reasoning 占 97~99%；`max_tokens` 16k 够用，2k/4k 会被 reasoning 吃光 |

**分工（拍定）**：**LLM 只做「读数字」和「关键决策点决策」；位置与落点一律本地。**

| 层 | 谁 | 依据 |
|---|---|---|
| 读数字（费用 / 卡排 / 上限） | LLM | 实测稳 |
| 数敌人总数 | LLM，但**先由本地确认"有没有敌人"** | 空场会幻视 |
| 敌人 / 我方位置 | **本地** | LLM 三次三种分法 |
| 部署落点 | **本地** `tile_map.project` | PA-1 上已验证能放准 |
| 执行 | **本地**两段慢滑 | 见 `SKILL_EMULATOR_OPS.md` §4 第 6-9 条 |
| 决策 | LLM，**仅关键点 3~5 次/局** | 延迟硬约束：全帧调 = 一局 7~15 分钟 |

两条硬约束（设计时必须让开）：
1. **延迟**：一局 15~30 帧 × 平均 30s 不可行 ⇒ 只能压在关键决策点（与本项目既有的"视觉预算 10 次/局"吻合）。
2. ⚠️ **暂停帧上本地 ONNX 也失效**：暂停压暗后 `operators_det` 检出 0（1080p / 720p 都试过，非暂停帧正常）
   ⇒ 暂停帧**不能**拿"ONNX 没检出"当"没有干员"的证据。
   **已找到替代**（2026-09-18 实测，`data/test_battle_pa2.png`）：按**血条颜色**找 —— `(B-R)>25 & (G-R)>10 & B>90`，3×9 闭运算 + 连通域过滤（宽≥70、高 6~26、面积≥400）⇒ 该帧恰好检出 2 条（真值 2）、零假阳，血条尺寸固定 125×7。

## 8b. 闭环分段验证（2026-09-18，执行与感知分开验）

在 PA-1 演习暂停态做「执行 + 感知分开验」（用户提的验收形状）：

- **执行（本地）✅**：暂停中依次放 2 个干员（狙击→高台 `(4,4)`、特种/近卫→地面 `(5,3)`），每次都用 `tile_map.project ×1.5` 定位 + 两段慢滑。**每次部署有三条独立信号同亮**：`残り配置可能数` 8→7→6、费用 47→40→31、卡排 12→11→10。
- **感知（LLM）⚠️**：对同一帧（真值 费用 31 / 我方 **2**）只问两题 —— 无提示答 `31 ✅ / 0 ❌`，加提示答 `31 ✅ / 1 ❌`。
  ⇒ **费用稳；我方干员计数在暂停帧上两次都不准（少数）**，加提示只能从 0 补到 1。
- 结论：**「我方干员几个」也必须本地兜**（血条配方见上），LLM 在这题上不能单独用。

## 8c. 敌人感知：MAA 没有敌人检测，「算」才是主力（2026-09-18 实测）

**问题**：血条只标受伤的单位，那满血敌人怎么看见？先查 MAA 有没有敌人检测。

**① MAA 没有敌人检测 —— 三条硬证据（不是"文档没写"）**：
- `MaaCore.dll` 里 `enemy` / `ENEMY` / `敌人` / `敌方` / `敌对` **全部 0 命中**；对照组 `operators_det`、`skill_ready_cls`、`deploy_direction_cls`、`BattlefieldMatcher` 都有命中 ⇒ 检索方法有效。
- MAA 的 ONNX 集**只有 3 个**（干员检测 / 技能就绪 / 部署朝向），资源包里**没有任何敌人模板**。
- 39MB 实战日志里 `enemy` **0 命中**；战斗侧实际调用过的识别器只有 4 类：
  `BattlefieldClassifier::skill_ready_analyze`(30664) / `BattlefieldMatcher::pause_button_analyze`(26662) /
  `oper_role_analyze`(242, 干员职业图标) / `kills_analyze`(1, OCR 击杀数)。**唯一与敌人相关的量是"击杀计数"**，
  那是"打死了几个"，不是"场上有谁、在哪"。
- 附带：MAA 自带的 `battle_data.json` 只有 `chars`（干员职业+攻击范围）与 `ranges`（范围形状），**没有敌人数据** ⇒ MAA 侧也没有"算"。

**② 满血敌人确实没有血条**（4 倍放大证实：`data/test_battle_pa2.png` 里那只 バール巡回者 上下都没有条）
⇒ 血条法**只能看已受伤的**。

**③ 但 LLM 能看见满血敌人**：PA-1 那帧的 5 个敌人**全程满血**（0/19 击杀 + 全程暂停），LLM 三次都答对「5 个」。

**结论：敌人感知分层，不是二选一**——

| 要什么 | 谁给 | 依据 |
|---|---|---|
| 敌人**是否存在 / 几个** | **LLM 看** | 满血也看得见，PA-1 帧 3/3 全对 |
| 敌人**位置** | **算**（出怪表 + 移速 → 第 N 秒在第几格） | MAA/本地都无检测能力；LLM 位置是噪声 |
| 受伤个体的**位置校准** | 血条颜色（本地） | 血条只对受伤单位出现 ⇒ 正好当"算 vs 实际"的校准点 |

**「算」的原料已就绪（不只是可行）**：
- `data/_level_*.json` → `waves[].fragments[].actions[]`，SPAWN 带 `key`(敌人id)/`count`/`preDelay`(秒)/`interval`/**`routeIndex`**(0..25 条路线)。
- `tools/enemy_speed.py` 已把移速换算成到达时间，**换算系数 1.0 是用实测对账过的**（T+3 出怪 → T+10.27 到门，与实测吻合）。
- `data/_enemy_db.json` 2151 个敌人带 `moveSpeed`。
- ⚠️ **唯一缺的**：PA 的关卡数据（本地有 act16side / act54side，**没有 act51side**）⇒ 要在 PA-1 上跑"算为主"，先补这一步抓取。

## 8d. PA 数据 + 位置表 + 对账（2026-09-19）

**① 数据抓齐（复用现成方式，没另起炉灶）**：`tools/workspace.py::ensure_level` → Kengxxiao/ArknightsGameData 镜像
`levels/<levelId>.json`。PA 共 **17 个带战斗的关**：`act51side_01..08` / `act51side_ex01..ex08` / `act51side_tr01`

**位置表的标准判据（2026-09-19 落定，用户拍板口径）**：

```python
def match_rate(predicted_cells, observed_cells, tolerance=1):
    """预测格集 vs 观测格集的重叠率。判据：≥ 80% 算对。

    tolerance：切比雪夫（棋盘）距离允许的格差 —— 1 格是**模型固有粒度**（敌人 1.33s 走一格，
    T 的 ±0.5s 不确定度换算过来就是 ±0.4 格），不要求 100%。
    """
    if not predicted_cells:
        return 0.0
    return sum(1 for p in predicted_cells
               if any(max(abs(p[0]-o[0]), abs(p[1]-o[1])) <= tolerance for o in observed_cells)
               ) / len(predicted_cells)
```

用法：拿 `enemies_at(stage, T)` 的格集与帧里读出的格集算这个比率，**≥80% 即视为位置对得上**；
低于 80% 才需要查（先查 T、再查该路线的路径）。

**✅ 真实用例验证（2026-09-19，`data/test_battle_pa3.png`：实测 T≈39s，观测 6 格）**：

| T | 预测数 | 容差1 预测→观测 | 容差2 | 观测→预测(容差1) |
|---|---|---|---|---|
| 38.50 | 6 | 67% | 100% | 100% |
| 38.75 | 6 | 67% | 100% | 100% |
| **39.00（实测点）** | 5 | **60%** | 100% | 100% |
| 39.50 | 6 | **83%** | 100% | 100% |
| 40.00 | 7 | 71% | 86% | 83% |

- **容差 1 + 直接用实测 T**：60~83% —— **卡在 80% 线附近**，对 T 的 ±0.5s 不确定度很敏感；
- **容差 1 + 在实测 T 的 ±1.5s 窗内取最好**：**83% ✓ 通过**（T=39.5）—— **这是推荐用法**；
- **容差 2：几乎失效**（9×7 板上 6 个观测格的 ±2 邻域覆盖了大半张图）⇒ **别放大到 2**；
- 反方向（观测→预测，容差1）在 T=38.5~39.5 恒为 **100%** ⇒ 模型没有"漏报场上单位"，误差全在"预测的格偏 1~2 格"这一侧。

**T 精度提升的方法（记下，暂不实施）**：现在是"每 0.5s 采样 + 两点插值"⇒ ±0.5s。
要 ±0.25s 以内就用**费用计数跳变的边沿时间戳**：连续快采右下角费用 ROI 的**像素跳变**（不做 OCR，只做帧差），
第 k 次跳变 = `T = k × costIncreaseTime`，于是 T 直接由**跳变墙钟时刻**给出（而不是插值）。
⚠️ 阈值别读数字（艺术字体 `1` 会被 OCR 认成 `7`，实测踩过两次），只看跳变。

## 10b. ⚠️ 上面那张表的 T 全部偏小 —— 费用钟漏了"已花费用"（2026-09-19 修正）

**症状**：§10 那局报 `T≈65.0s 费用=75`，其实 T 大约是 **86**（差 21 = 那只已经放下的煌的部署费）；
连带 `敌人=7` 也是按 T=65 查的 ⇒ **报了错的位置/数量**（位置表本身没错，是喂进去的 T 错了）。

**证据链（两个独立时钟对上）**：另取一帧，费用 **19**；旧式 `T = 费用 − initialCost` ⇒ **9**。
但按**敌人位置反查**：画面里两只撬棍巡分别站在 `(3,0)` 和 `(5,0)`，而 `enemies_at()` 全时间轴上
**只有 T=30/31 会同时出现这一对** ⇒ 真 T ≈ **30**；差的 **21** 正是那只手动先放的煌（6★ 近卫）的部署费。
`clock(19)` 带上 `spent=21` 后返回 **(30.0, 'cost-10+spent21')** ✓ —— 费用钟与位置钟同时说是 30。

**修法（已落地 `tools/battle_loop.py`）**：
1. `T = 费用 − initialCost + spent`；`initialCost` 从关卡 `options` 读（**各关不同**：实测 3/5/10/15/20，
   写死 10 是错的），读不到就**不出 T**（fail-closed，宁可不报敌人位置）；
2. `spent` **自己测**：循环放人在暂停态做 ⇒ 前后两次费用读数之差**就是牌价**（暂停不 regen，
   这正是"费用差"当初失败的反面：跑动中测被回涨掩盖，暂停中测干净）。测不到就标 `spent_unknown`，
   T 的说明里带 `⚠️ 偏小`，不假装准；
3. 开局前已经手动放过的干员 ⇒ 用 `--spent` 声明（填**真实费用**）；填不出就用下面的反查法量。

**反查 T 的通用做法（拿敌人位置当钟）**：`for T in range(0,120)` 比 `enemies_at(stage,T)` 的格子集合
与画面上检出的敌人位置（同帧）——**唯一匹配的 T** 就是真 T（本次 0..70 里只有 30/31 命中）。
副产品：这同时校验了关卡数据→路径模型→投影→屏幕整条链。

- `options.moveMultiplier = 0.5` 是**全关卡统一**的（主线也是 0.5）⇒ 不是"漏乘系数"（曾怀疑时间表要减半）；

  ⇒ 费用钟在这些关直接失效，得换 `--spent`/位置钟。

## 10c. 费用 OCR 的真根因 = 暂停蒙层（2026-09-19 实测），以及 T 修好后的实跑

**症状**：同一 ROI（`(1798,741,120,66)` 设备像素）在**演练/暂停帧**读 `49` 成功、在**暂停的活帧**读 `19` 失败（返回 `None`/`亻`）。

**根因（量出来的）**：暂停蒙层把整幅画面压暗到 **×0.61**（全图均值 101.2 → 61.9）；
**运行帧 OCR 立刻读出 `20`**、暂停帧读不出。数字字形也有关系 —— 细笔画的 `19` 比 `49` 更容易被打字框切碎
（试过 1.4/1.8/2.2 倍亮度拉伸、二值化 150、Otsu、加灰边、upscale 2/3/4 —— 全都救不回来，**不是对比度问题**）。

**修法（已落地）**：`state()` 优先用**暂停帧 OCR**（决策那一刻，最准）；读不出就用
`cost_hint`（**运行帧**那次读到的值）+ 到暂停为止经过的秒数 × `regen` 折算，并在 `cost_src` 里**如实标出来源**；
`regen>5`（训练关 999）不折算（fail-closed）。循环每圈：恢复 → 睡 `step` → **抓一帧读费用** → 再暂停。

**修后实跑（3 圈，PA-1 演习，spent=21）**：
```
[1] T≈33.0s(cost-10+spent21) 费用=22(暂停帧 OCR) 卡排=11张 我方=1 敌人=5
[2] T≈36.0s(cost-10+spent21) 费用=25(暂停帧 OCR) 卡排=11张 我方=1 敌人=6
[3] T≈39.0s(cost-10+spent21) 费用=28(暂停帧 OCR) 卡排=11张 我方=0 敌人=6
```
T 与费用同步 +3/圈（step=2.0s + 抓帧耗时）、regen=1/s ⇒ **费用钟自洽** ✓；
规则在**第 1 圈**就被判定"干员已在 (5,3)" ⇒ 之后 `等待`（行为正确：作业只有 1 条规则）。

**仍未闭合（新记）**：① 我方血条检测在跑动帧会**闪**（`我方=1 → 1 → 0`）⇒ 靠它判"这条规则已完成"会在闪的时候误判
