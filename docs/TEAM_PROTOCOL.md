# 团队自组织协议（TEAM PROTOCOL）

> 目的：让队友在**遇到新问题时自己动手组织资源**，而不是等 Lead（或用户）发话。
> 用户 2026-09-24 明确要求：「队友怎么做到在没有我主动要求的情况下，自己遇到问题之后按需创建智能体团队和发布共享任务」。

## 一、每个队友（含未来的）都必须遵守的自组织规则

1. **遇到新问题，先建共享任务，再动手**
   - 用 `team_task_create`（**不是 Lead 专属**）写清：问题、证据、验收标准、写权限范围。
   - 若这个问题超出你当前任务范围，**不要私自扩大战线**：建任务 → 在任务里写清依赖 → 用 `send_message` 通知 lead。
2. **需要并行调研/验证时，自己开子代理**
   - `subagent`（或 `subagent_fork`）**任何队友都能调**：适合"独立验证我这边的结论""调研某个 API/MAA 行为""离线批量分析"这类自足工作。
   - 子代理产出**必须落到文件**（`docs/`、`runtime/reports/`）并在任务里引用，避免只在对话里说。
3. **需要新的队友时，走"申请 → Lead 创建"**
   - `spawn_teammate` **只有 Lead 能调**（工具层面的硬限制，不是流程偏好）。
   - 做法：`send_message` 给 `lead`，写清 **角色名 / 职责 / 为什么现有队友不够 / 建议的提示词要点 / 期望产出**。Lead 会立刻创建并把任务指给它。
4. **交接与冲突**
   - 同一个文件**同时只能有一个写者**：在任务里写清 `write_scopes`；要碰别人范围内的文件，先发消息约定。
   - 改完必须自证：语法检查 + 能离线测的离线测 + 把证据贴进任务。
5. **审计闭环**
   - 每个**新改动**都要有一个独立审计（可以由你开 `subagent` 做，或由 Lead 派 `auditor-*`）。
   - 审计结论落 `docs/audits/<时间>.md`。

## 二、为什么这样分工（事实说明）

| 能力 | 谁能用 | 说明 |
|---|---|---|
| `team_task_create` / `team_task_get` / `team_task_update` | **所有队友** | 共享任务板是全员可写的协作面 |
| `subagent` / `subagent_fork` | **所有队友** | 适合并行调研与独立验证 |
| `spawn_teammate` / `interrupt_agent` | **只有 Lead** | 工具层限制；队友需要就走"申请" |
| 模拟器（emu #1） | **Lead 独占**（串行） | 同一模拟器只允许一个 MAA；用户自己的 MAA（emu #0）任何人不许碰 |

## 三、Lead 的职责（对上面的配套）

- 每条 `send_message` 申请**当轮处理**：能建就建，建完把 task id 回给申请人。
- 新队友的提示词里**必须**包含本协议要点（自组织 + 写权限 + 不要动模拟器）。
- 每轮检查任务板：清理过期任务、把无人认领的任务指派或关闭。
