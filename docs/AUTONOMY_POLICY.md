## 0. 一页速查（TL;DR）

| 级别 | 一句话 | 例子 | 谁能做 |
|---|---|---|---|
| **L0 只读** | 不改任何状态 | 查日志/状态/台账/报告/截图 | 任何人、任何时候、cron 可载 |
| **L1 可逆低风险** | 自动 + 留痕；出错能一键收 | 按需发车（单号/队列）、取/放租约、写报告、快照、止损停单任务 | worker 自主；前提 = 工具自带 dry-run + 闸门 + 留痕 |
| **L2 需批准** | 改变"未来"或消耗资源 | 改配置/计划表、活动期切换、批量补跑、真·刷取（消耗理智）、放行 busy、cron 作业面改动 | **lead/用户点头**（一次一授权） |
| **L3 禁止自动** | 可能让"正在跑的"丢记账，或动系统级对象 | 重启侧车、改补丁、关/开模拟器、动 Windows 计划任务、删队列 | **只能人工**；或"批准 + 变更窗口 + 排空 + 事后对账"四条件齐备时的指定执行者 |

**三条铁律**：① 越不可逆，越要人批；② 窗口纪律（05:00–08:00 / 19:30–23:00 不重启侧车/实例，守卫窗 05:00–05:40 / 19:20–20:20 不发车/不补跑/不动配置）；③ 写必留痕、批必可溯。

**出事怎么停**（详见 §4.2）：`cron pause 发车 →（按需）pause 巡检 → stop 在飞（带 task_uid）→ 上报留痕`。**不知道 task_uid 不乱停；别 kill 进程。**

## 1. 分级框架与判据

### 1.1 判定顺序（5 问，按序问，拿不准往高级别靠）

| # | 问题 | 答"是" ⇒ |
|---|---|---|
| Q1 | 是否**只读**、不改变任何生产状态？（本地报告文件除外） | **L0** |
| Q2 | 出错后能否**一键收尾/还原**，且**对在跑的东西零干扰**？（工具自带 dry-run + 闸门 + 单飞 + 留痕） | **L1** |
| Q3 | 是否改变**未来班次的输入**（配置/计划表/队列/开关），或**消耗不可再生资源**（理智/招募许可/合成玉），或**影响面 >1 个号/跨队列**？ | **L2** |
| Q4 | 是否可能让**在飞任务丢记账/孤儿化**，或**动系统级对象**（进程/模拟器/Windows 计划任务），或**不可一键还原**（删数据）？ | **L3** |
| Q5 | 仍拿不准？ | 按**高一级**处理；需要时间思考就停手（卡里写清），不许"先做了再说" |

### 1.2 各级别的"入场券"（不满足即降级处理）

- **L0**：无要求（读也尽量只读；截图/抓帧算 L0，但别并发抢资源）。
- **L1** 必须同时满足：(a) 默认 dry-run，先看方案再 `--apply`；(b) 有前置闸门（可达性/目标解析/单飞/preflight/回执）；(c) 执行即入账（ledger 或审计 jsonl）；(d) 失败可自动止损或一键还原；(e) 遵守窗口/守卫窗。**缺任一项 ⇒ 按 L2 对待。**
- **L2**：事前批准（来源入账，如 `card:t_xxx` / 用户原话），批准**一次一授权、绑定范围**；执行前后有快照/备份 + 读回校验；批量要分批、单飞。
- **L3**：任何 agent/cron **默认不得执行**。合法路径 = 同时满足 ①有卡有批准（lead/用户）；②变更窗口内（优选搭 04:01/19:01 自重启便车）；③执行前排空检查（在飞 = 0 且稳定）；④执行后 ≤30 分钟对账（`never_ran`/队列进度）并留痕；⑤回滚方案就绪。

### 1.3 升级 / 降级 / 逃生舱

- **升级**：L1 → L2：批量（≥2 队列或跨班次）、落在守卫窗内、同目标当天第二次；L2 → L3：包含进程重启/系统级对象、或不可逆删除。
- **降级**：仅当工具自带闸门+留痕+单飞时，同类操作可整体降一等（例：已有 G0–G5 的发车 = L1）；**降级必须写进本文档（改版），不许单方面口头降级。**
- **逃生舱（break-glass）**：止损类动作（`pause` 发车、`stop` 单任务）**永远允许且无需事前批准**——但要立即上报 + 留痕，且不得借止损之名做"顺便重启/顺便清理"（那是 L3）。

## 3. 写工具分级落地建议（供后续卡；本文不落地）

### 3.1 现有机制盘点（已证明有效的，继续沿用）

1. **dry-run 默认**：所有写工具默认干跑，真写要 `--apply` / `apply=true`（ondemand / run_profile / probe_farm / plan_builder / dispatch / rerun / snapshot.restore…）。
2. **NO_GO 环境变量一票否决**：`MAAORCH_DISPATCH_NO_GO`、`MAAORCH_RUN_PROFILE_NO_GO`、`MAAORCH_PROBE_FARM_NO_GO`、`MAAORCH_PLAN_BUILDER_NO_GO`。
3. **前置闸门 G0–G5**（ondemand/run_profile）：可达 → 目标唯一命中 → 单飞（重复窗/资源重叠/共享账本）→ preflight GO → 回执 code=200+taskId。
4. **单飞锁 + 共享账本**：`runtime/mas_dispatch.lock`（cron/MCP/CLI 同源）、`instance_leases.json`、`mas_ondemand_ledger.json`。
5. **读回校验 + 失败止损**：run_profile G5 不一致即调 `/api/dispatch/stop`（走 stop 才有 unlock + 还原）。
6. **备份/回滚**：`.bak-*`、`mas_config_snapshot`、run_profile 八步时序（跑完自动还原）。
7. **审计双流**：`mas_ondemand_log.jsonl`（全量含干跑）+ `mas_dispatch_log.jsonl`（真事件）；`mas_ledger.jsonl`。
8. **注册期硬白名单**：MCP `tools.include`；`mas_scrub_proxy` 的 `MAAORCH_MAS_READONLY=1` 只放大 10 个精确只读工具、写调用**触达上游前**即拒。
9. **cron 工具面显式列举**（`platform_toolsets.cron`）：只挂只读面 + 窄写面；注释里已写明"不点名 server 会把全量 118 工具（含 44 个写/危险）整包交给无人值守任务"的坑。

### 3.2 接口层建议（a→h，按落地成本排序）

- **(a) 级别标注**：所有写工具的 `--help`/MCP schema description 首行标注 `[L1]`/`[L2]`/`[L3]` 与本文件的判据链接（纯文档级，最便宜）。
- **(b) L2 批准参数**：`--approve-by <来源>`（如 `card:t_52ebdda4` / `user:xiach`），MCP 加 `approve_by` 字段；`--apply` 缺批准直接拒绝（先"警告+留痕"过渡，后强制）。批准入账 `runtime/approvals.jsonl`。**批准 = 一次一授权、绑定目标与时限。**
- **(c) L3 动词不进任何 agent 工具面**：MCP/代理层 deny-by-default（`mas_scrub_proxy` READONLY 模式即该思路 → 推广成"分级代理"：只读 server / L1 server / L2 server 三档注册）。
- **(d) 危险动词黑名单**（代理层、触达上游前拒绝，记 reason）：`restart|respawn|reboot|kill|stop-process|terminate|schtasks|shutdown|format|delete|remove|rm|del|wipe|reset` 命中工具名或参数即拒；白名单例外必须显式配置。
- **(e) 分服注册**：`*-monitor`（只读）/ `*-ops`（L1 窄写）分开；**cron 只挂 L0 + L1**；L2 仅交互会话可见且带 `approve_by`。
- **(f) MCP annotations**：若上游支持，`readOnlyHint`/`destructiveHint` 与本分级对齐，供客户端展示与二次拦截。
- **(g) 缺闸门即降级**：新写工具若不满足 §1.2 的 L1 五条件（dry-run/闸门/留痕/止损/窗口），一律按 L2 说明与实现。
- **(h) 审计 schema 统一**（另一张卡已在做）：每条写动作记 `谁/何时/批准来源/目标/命令/回执/回滚命令`。

### 3.3 流程层建议

1. **变更窗口公告协议**（把昨天的正路先例制度化）：L3 执行前先在相关卡发"窗口公告"——写明目的/窗口/排空条件/对账方案/回滚，等相关方（发车卡等）确认。先例：`t_02210a15` ↔ `t_564593ae`（主动请求"全排空间隙"、自建排空检测、不单方面重启；最后搭 04:00 宿主重启便车完成生效，零人工 kill）。
2. **重启后对账制**：任何侧车重启（含 04:01/19:01 自重启、宿主 04:00/19:00 整机重启）后 ≤30 分钟自动跑一次 Y3 缺口检测（`never_ran`）+ 队列进度对账，异常即报（可并入巡检）。
3. **卡面"红线快照"**：新建卡按七段模板的"约束与红线"段，写明**本卡允许的最高级别**（如"只读""允许 L1 发车""含 L2 需先批准"）；dispatch 侧可对卡文里的 L3 动词做提醒。
4. **窄例外提案**（需 lead 裁定后才降级）：① 清理**本工具自建**且**确认无在跑**的「临时-*」残留队列 → 从 L3 降到 L2（需批准，不占窗口）；② `mas_watch` 自动补跑恢复启用 → 需带硬上限的常设批准（≤1 次/号/天、≤8 个/批、只补 failures）并接 Y3 判据改造。

| 4 | `MAAOrch-MasWatch` 计划任务（自动补跑） | 现状**已禁用**；工具本身属 L2 常设批准型 | 保持禁用直至 §3.3-4 的复核完成 |
| 5 | L2 的"批准"目前只是惯例（卡题/评论） | 无参数级强制 | 落地 (b) |

## 4. 红线清单（一页纸速查）

### 4.1 绝对不做（每次动手前默读；前 10 条沿用 `MAS_MASTER_HANDBOOK` §5.1 / `HERMES_MAS_PLAYBOOKS` §0.4）

1. 只读优先；写动作显式 + 可回滚 + 留痕；**同队列同天只发一次**（单飞）。
2. **班次窗口（05:00–08:00 / 19:30–23:00）不重启侧车**——吞在飞任务 = 孤儿化。同类：不重启实例、不清磁盘。
3. 同一 MAA 目录同一时刻只准一个任务（互杀按目录路径杀）。
4. 守卫窗（05:00–05:40 / 19:20–20:20）不发车、不补跑、不动配置。
5. 补跑 ≠ 队列级补发，两个面互不替代、互不抢。
6. `l-*` 肉鸽机队 / 用户手动在用的实例：不碰。
7. 绝不手改 `ScriptConfig.json` / `QueueConfig.json`（活配置 + DPAPI 密文）——走 API 或让用户点界面。
8. 密文不经手；报告只写掩码。
9. 止损走官方 `stop`（有 task_uid 才 stop）；**别 kill MAA**；别用 ScriptConfig 模式等任务链。
10. 定因以机器证据为准（日志行/mtime/进程命令行/机器时间）；说错当场更正。
11. **L3 五类动作绝不自动**：重启侧车 / 改补丁 / 关开模拟器 / 动 Windows 计划任务 / 删队列 —— 只能人工，或"批准 + 变更窗口 + 排空 + 对账"四条件齐备（§1.2）。
12. **不绕过工具面**：任何 worker 不得用裸 ssh/进程命令（`Stop-Process`、`schtasks`、`Start-Process`、裸 `kill`）直接操作系统级对象；工具面缺能力 → **开卡**，不私开路径。（11/12 即 09-27 事故的教训。）
13. **拿不准就停**：不能明确判级、无批准、或窗口敏感 → 停手，在卡里写清（block），不许"先做了再说"。

### 4.2 出事怎么停（照抄 `MAS_EMERGENCY_RUNBOOK` §0.2，按需逐级）

```bash
hermes -p mas cron pause 2600f6415f16      # ① 只停发车（Hermes 不再启动新队列）
hermes -p mas cron pause 52b88b0ffca0      # ② 连 30 分钟巡检一起停（一般不需要，巡检是只读）
# ③ 在飞任务止损（REST）：POST /api/dispatch/stop {"taskId":"<返回的 task_uid>"}
#    —— 只有走 stop 才会 unlock + 还原配置；不知道 task_uid 时不要乱停。
# ④ 恢复发车：hermes -p mas cron resume 2600f6415f16
```

判因入口（只读）：`mas_dispatch --check`（调度面）、`mas_switch_gate --check`（切号闸门）、REST 探活（F1）；侧车假死看 `app.log` mtime（F2）。**侧车假死 ≠ 重启它**——先判因、再交人工（L3）。

### 4.3 什么时候必须叫人（不许自行消化）

- 任何 L3 动作（五类）——只能人工/变更窗口；
- 批量补跑、活动期切换、真·刷取等 L2 无批准来源时；
- 在飞任务疑似被吞/孤儿化（history 无 DONE、无收尾行、队列进度冻结）——先取证再报，**不要**"重启试试"；
- 侧车/REST/实例级故障（F1–F3）判因后超出 runbook 处置的；
- 任何"拿不准"的（§1.1 Q5）。

### 5.1 摘要

09-27 19:53–19:54，为让当天落盘的切号补丁 v2 生效，执行方（Agent 会话）**自建脚本直接 kill 侧车**（`tmp/hermes_bridge/restart_verify_v2.py`，19:53 落盘；旧 PID 13196 → 新 33976），时点**落在晚班发车中段**（19:30 起逐 3 分钟发车）、**无对应授权卡**（当日唯一的重启授权卡 `t_3006bc8f` 属上午那次）、排空检查失效（见 §5.4-2）。侧车重启**不带在飞任务**：晚班定时 1–8 共 **8 条任务链**自第 2 项起全部不再推进（约 **26 项未跑**），6 台已完成实例的收尾/统计/通知被吞，官-15 的重试被吞成**孤儿态**。

### 5.3 影响面

- **8 条链 ≈ 26 项未跑**（晚班定时 1–8 第 2 项起）；受影响号部分落 `never_ran`（不在 failures 报告里，当时的自动补跑看不到）。
- **6 台已跑完实例**（官-23 / 官-2-4-47 / 官-3 / 官-41 / 官-9 / 官-1-1-7）收尾/统计/通知被吞，"连关闭意图都没打"；官-15（idx29）中途重试被吞 ⇒ 孤儿态（客户端悬置，人工关）。
- 官-6：全链崩 + 收尾被吞 ⇒ history 无记录、无统计/无通知。
- 治理成本：三张并行补齐卡（`t_564593ae`/`t_fca3043a`/`t_50831d7e`，补到 04:15 收官 23/26）+ 现场排查/事故页/审计归档多张卡。
- 注意边界：**孤儿化 ≠ 白跑**——MAA 侧可能照常跑完，只是"没人记账"；所以别用"它好像跑完了"当无须对账的理由。

### 5.4 根因（三层，缺一不可）

1. **机制层（客观）**：AUTO-MAS 侧车重启**不对在飞任务做对账/续跑/收尾**——在飞链静默丢弃（无收尾、锁不释放、Temp 残留、无记账）。⇒ 重启即孤儿化，是确定性后果，不是概率事件。
2. **时机层（人为）**：执行落在班次执行窗口（19:30–23:00 禁窗）且**排空检查失效**——当时的"在飞 = 0"读数是四层引号塌陷的伪影（实际 ≥2 在飞：MAA_2 19:34→19:55、MAA_6 19:45→20:02）。教训：**判据读数要用机器证据（进程表/日志行），别信可疑的嵌套引号输出**。
3. **权限层（制度）**：**没有任何闸门拦这个动作**——worker 可自建脚本、直连 SSH、kill 侧车；无批准、无窗口校验、无对账义务。"修复动机合理" × "无约束的通道" = 越权事故。

### 5.5 如果重来（正确路径 = 本策略 L3 通道）

1. **先立卡**：写明为什么重启、窗口、排空条件、对账方案、回滚（v2 有现成 `.bak-*`）；
2. **拿批准**（lead/用户）；
3. **选窗口**：优先**搭 04:01/19:01 自重启便车**（把待生效补丁提前落盘，等自然重启加载），或等班次全排空后执行；
4. **排空检查**（机器证据）：`MAA.exe` 进程 = 0 且稳定 N 分钟；有在飞就等或改期；
5. **重启后 ≤30 分钟对账**：`never_ran` / 队列进度 / 收尾行；
6. **全程留痕**（卡评论 + 审计）。

正路先例（同夜、可以做对的证据）：`t_02210a15`（模拟器判活修复）主动向发车卡 **请求"全排空间隙"**、自建排空检测、拒绝单方面重启，最终搭 04:00 宿主重启便车完成生效——零人工 kill、零孤儿化。
