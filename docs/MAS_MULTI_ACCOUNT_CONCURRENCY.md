## 1. 机制结论（源码为准，本地 v5.4.0 与生产端已比对）

### 1.1 为什么"同一脚本的多账号"不可能并发

三处硬约束，逐条给出源码位置：

1. **任务级锁（脚本粒度）**
   - `app/models/task.py:221` —— `Task.prepare()` 里 `raise RuntimeError("任务已在运行")`；
   - `app/core/task_manager.py:318-320` —— `add_task` 对**脚本级**目标：`if script_uid is not None and Config.ScriptConfig[script_uid].is_locked:` → 抛「任务 X 已在运行」；
   - `app/core/task_manager.py:176` —— **队列任务**在 `main_task` 循环里逐脚本检查 `is_locked`：已锁定的脚本**跳过**（不是并发，是跳过）。
   - 即：**同一脚本同一时刻最多一个任务**，第二条路（不管走队列还是直接发脚本）都会被拒或跳过。
2. **任务内逐用户串行**
   - `app/task/MAA/manager.py:182-189`：
     ```python
     for self.script_info.current_index in range(len(self.script_info.user_list)):
         task = METHOD_BOOK[self.task_info.mode](...)
         await self.spawn(task)   # 顺序 await —— 前一个用户跑完才轮到下一个
     ```
   - 每个用户内部：`app/task/MAA/AutoProxy.py:410-440` —— 两种模式 `["Annihilation", "Routine"]` 各自 `1..RunTimesLimit(3)` 次尝试；`L1080` —— 两模式未全成则 `用户 ... 的自动代理任务未完成`（用户级失败标记，任务继续下一个用户）。
   - 即：4 个号的 4 份工作量在**一条任务里串成一条时间线**——这就是"一轮 1.5–2 小时"的结构性来源（今日尾部实例实际到 3h50m，§2.1）。
3. **"已在运行"拒绝逻辑的边界**：拒绝发生在**脚本级目标**；队列任务里则是"跳过已锁脚本"。所以**不存在**"同一脚本塞两条队列并行"的玩法——第二条要么被拒、要么被跳过。

### 1.2 并发实际约束只有两条（外加一条纪律）

| # | 约束 | 依据 | 规避方式 |
|---|---|---|---|
| 1 | **一脚本同时刻一任务** | §1.1 的锁 | 拆成 N 个脚本，一号一脚本 |
| 2 | **一 MAA 目录同时刻一任务** | 换号/重试/中止按**目录路径杀进程**：`开始中止进程: E:\MAA-Multi\MAA_6\MAA.exe`——同目录并发=互杀（今日 06:31 实证，§2.4） | 每个并发脚本**自带目录**（备用 MAA_13/14/25/28） |
| 3 | *（纪律，非代码）* **一实例同时刻一任务** | 源码中**没有实例级锁**：两个脚本（不同目录）指向同一实例时，AUTO-MAS 不会报错，两个 MAA 会同时 adb 点同一台设备——静默互踩 | 借用实例必须保证**借用窗口内原主不跑** |

> 生产端核对：`app/task/MAA/manager.py`、`app/core/task_manager.py`、`app/models/task.py` 与其 v5.4.0 发布哈希**一致**；差异文件只有 `AutoProxy.py` 与 `general/manager.py`（预期：切号 v2 补丁所在）。

### 1.3 因此，"把 4 个号拆到 4 个实例同时跑"的正确形态

**N 个单号脚本 × N 个 MAA 目录 × N 个实例 × 并发发车**——四个条件缺一不可。任务形态不是"改 AUTO-MAS 让它支持并发"，而是**用现有机制把串行工作拆成 N 条互不相干的独立时间线**。

### 3.3 需要哪些改动

**A. AUTO-MAS 配置（人工，界面操作）**
1. 复制 官-1-1-7 → 新建 3 个单号脚本（建议命名 官-1-1-7-<号>，便于运维认读）；`Info.Path` 分别 = `MAA_13 / MAA_14 / MAA_25`；`Emulator.Index` = 3 台借用实例；各留 1 个号（从原脚本**移出**该号：移动用户=新脚本建用户 + 原脚本删/禁用，密码 DPAPI 字段不复制、留空后续由用户补——**红线段落见 §4.2**）。
2. 每个新 sid 补 `data\<sid>\Default\ConfigFile`（从任一现役脚本复制整目录）。
3. 每用户配置逐项核对（StartUp 开关、剿灭/日常任务列表、用药、`RunTimesLimit=3`、`RoutineTimeLimit`）——以现网 官-1-1-7 的模板为准。
4. 原脚本保留的号（1 个）继续走 日常定时6/晚班定时6；**其余号当天起不得再出现在原脚本**（防双跑，§4.1-R1）。
5. `实例绑定` 归属变更登记：借用实例（如 i25/i28/i31）从 l-* 移交给新脚本——同步进实例↔脚本映射（见 C-3）。

**B. 发车（三选一，推荐 ①起步 → ②长期）**
1. **过渡（最小落地）**：Hermes cron 新增一条 job（05:15/19:45 与位6 同刻或错峰 1–2 分钟），逐条调用 `tools/mas_ondemand.py --script <新脚本> --apply`（4 条）。按需工具的闸门天然覆盖：`DUP_WINDOW` 同目标拒绝、`slot_busy`（目录/实例与在跑进程重叠拒绝）、实例租约（`tools/mas_instance_lease.py`，碰实例先 acquire——4 台不同实例=4 条互不冲突的租约）。
2. **长期（推荐）**：扩展 `tools/mas_dispatch.py` 的 `SHIFT_TABLE`：新增「并行组」条目（例如 `日常并行6a/6b/6c` → 4 个脚本级 dispatch，05:15 同刻下发），白名单 `QUEUE_RE`（现 `^(日常|晚班)定时([1-9]|1[0-2])$`，L104）与 `--check-schedule` 一并扩展。**这是代码改动，按 L2 走审。**
3. **临时队列路线**：`--account` 的账号级临时队列机制（今日 06:31 的先例）拆号后天然"一号一脚本一目录"，4 条临时队列可并发——但现状纪律是「**同一时刻只跑 1 条临时补跑队列**」（`docs/HERMES_MAS_PLAYBOOKS.md:151`），要用于并发需**显式改这条策略**；且临时队列是"临时"语义，不应成为稳态排班。→ 只建议做试点/补跑，不建议当铺开主线。

**C. MAAOrch 配套**
1. 巡检/日报期望集：`mas_dispatch --reconcile` 的 EXPECTED 集合、错误日报、`SWITCH_GATE`（新脚本的注入校验仍应是"官 masked+true"）——不同步会误报"缺发车"。
2. 实例租约登记：借用实例写进租约台账（补跑/工具箱不会去抢）。
3. **实例↔脚本映射失真点**：`tools/mas_ondemand.py` 的"实例→目录"反查（`_recent_activity`）按"第一个 emu 匹配的脚本"归位——借用后同一实例挂两个脚本（原主 + 借用方），该判据会归错目录。需要把 t_ee50913f（权威映射表）接进来消歧义；否则 G3 的"最近活动"提示会失真（`slot_busy` 的目录直查不受影响）。
4. l-* 让位确认：若肉鸽机队还要用 l-1..l-7，则剔除这三台候选，从"新建实例"路线补（改磁盘/内存账）。

### 3.5 最小验证步骤（先拆 **1 个号**，12:30 空闲窗）

**前置（Go/No-Go，4 项）**
1. **归属确认**：lead/用户确认 l-* 肉鸽机队不再使用本机 l-1..l-7（否则换实例方案）。
2. **版本对齐**：目标备用目录 MAA 对齐到现网在跑版本（或实跑一次验证兼容），并补 `data\<sid>\Default\ConfigFile`。
3. **内存实测**：在 05:15–06:30（或晚间等效峰）用 `tools/host_health.py` 连采 ≥3 枪，确认 Δmem 可承受（阈值 lead 定；参考低载空闲 47.6GB）。
4. **登录记录**：目标号在目标实例（如 i25）的客户端**人工登录一次**（进大厅即可）——这是拆分的硬前置，无法绕开。

**试点（9 步）**
1. 新建测试脚本「官-1-1-7-测试」（Path=MAA_13，实例=i25），含 1 个号（建议选尾号 him 或 汐影月k）。
2. 补 `data\<sid>\Default\ConfigFile`；核对用户配置与现网一致。
3. **从原脚本移除该号**（禁用原用户；当天该号只存在于新脚本——否则同日双跑，§4.1-R1）。
4. 只读预演：`tools/mas_ondemand.py --script 官-1-1-7-测试`（dry-run），确认 4 道闸门（G1-G4）与 slot 检查通过、实例租约可 acquire。
5. **人工批准后真发车**（12:30 空闲窗，按需脚本级）。盯 `app.log` + 备用目录 `debug\gui.log`。
6. 跑完后的验证（全部要过）：
   a. **身份**：标题页/大厅 ID 帧 = 该号 UID（`tools/mas_identity_trace.py` 对照基线，防静默错号）；
   b. **记账**：`history\2026-09-28\<账号名>\官-1-1-7-测试-….log` 且标记 `Success!`；
   c. 通知/统计报告按新脚本名发出、内容正常；
   d. 全程无「MAA 在完成任务前退出」/互杀记录（`slot_busy` 类）。
7. 次日复核一轮（含晚班），确认与原队列无资源重叠、巡检不误报。
8. 通过 → **2 路**（原脚本留 2 号 + 新脚本 2 号）→ 再复核 → **4 路**。
9. 每步只改一处、跑后复核；任一步失败就地停手上报（不叠加改动）。

### 3.6 回滚（<10 分钟，全人工）

1. 新脚本停用/删除；2. 该号恢复到原脚本（启用原用户）；3. 借用实例从租约/映射中摘除（归还 l-*）；4. 发车侧 cron/表项撤下；5. 复核一轮产线（确认位6 队列恢复正常）。

## 4. 风险与红线

### 4.1 风险表

| # | 风险 | 等级 | 判据/规避 |
|---|---|---|---|
| R1 | **同号双跑互踢**（同一账号多实例登录会互相踢下线） | 高 | 拆号当天清原脚本；工具侧已有 fail-closed：`mas_ondemand` 一号命中多脚本 ⇒ 拒绝（L278）；补跑按账号名定位，多脚本命中会被拒——是特性不是 bug |
| R2 | **同目录并发互杀** | 高 | 今日 06:31 实证（§2.4）。拆分脚本**只用备用目录**；红线：不得与 MAA_1..12 任何队列项共用目录 |
| R3 | **实例绑定被破坏** | 中 | ① 借用期原主若跑 ⇒ 同实例双 MAA 静默互踩（**无锁**）；② 原客户端登录态被覆盖（l-* 的日服号需重登才能回归）；③ 实例↔脚本映射 1:N 后巡检判据失真（§3.3-C3） |
| R4 | **资源竞争** | 中 | +3~4 路并发落在 05:15–06:30 峰值窗；内存实测缺样（前置 3）；MuMu 实例总量 55、C 盘紧张 |
| R5 | **记账/通知口径** | 低 | 4 份报告/统计、映射表更新（§3.4）；巡检期望集不同步会误报 |
| R6 | **切号静默错号** | 中 | 单号脚本+记录缺失 ⇒ 静默跑当前登录号；试点 ID 帧验证 + 常态化 IDENTITY 留痕 |
| R7 | **发车时序** | 中 | 宿主 04:00/19:00 计划重启（事件 1074）——错峰到 04 段需避开；与产线同刻会叠峰；推荐试点用 12:30 空闲窗，稳态后再选同刻/错峰 |
| R8 | **拆号期间的产线扰动** | 低 | 拆号操作本身要改脚本/队列：建议在非班时段做（如 13:00-14:00），并先跑 `mas_dispatch --check` |

### 4.2 红线（绝对不做）

1. **不用 MAA_1..12 跑拆分脚本**——那是 12 条产线队列的目录，同目录=互杀。
2. **任何时刻，一个号只在一个脚本/一台实例上跑**——拆号必须"先移出、再启用"，绝不双在。
3. **新脚本必备 `data\<sid>\Default\ConfigFile`**——否则秒退+占用队列时序（l-* 的现实教训）。
4. **借用实例排他**：借用窗口内原主（l-*）不得运行；借用前把例外的可能路径（临时队列/补跑/巡检触发）全部封住。
5. **不引入"同实例双跑"**——没有锁，出了事连报错都没有。
6. **一切以 ID 帧/UID 核对为验收**——不做身份验证就不算拆成功。
7. 试点窗口避开：班组高峰（05:00–09:30 / 19:30–24:00）、宿主重启窗（04:00/19:00 ±30min）。
