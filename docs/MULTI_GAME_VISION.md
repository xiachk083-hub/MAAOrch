## 2. 平台定位（2026-08-14 用户拍板）：MAAOrch = 调配平台，引擎 = 黑盒

「主要还是我们项目，我们项目就是调配其他这些东西的」——MAAOrch 不深耦合任何
引擎，**所有引擎（MAA.exe / MaaEnd / M9A）都是被调配的执行器**：

```
MAAOrch（编排层 — 唯一平台）
  ├─ 调度台/队列/实例池/模拟器状态机/恢复链/统计/EventBus（游戏无关，已有）
  ├─ 引擎适配器（每引擎一个薄壳，与方舟现有模式同构）
  │    ├─ maa_arknights：注入 gui.json → 启动 MAA.exe → LogWatcher 读 asst.log
  │    │   → 事件判定（已有，不动）
  │    ├─ maa_endfield：注入 MaaEnd 配置 → 启动 → 日志/心跳监控 → 完成判定（待建）
  │    └─ maa_r1999：注入 M9A 配置 → 启动 → 日志/心跳监控 → 完成判定（待建）
  └─ 游戏账号体系（game_client 字段已预留，队列/统计按客户端分流）
```

每个适配器只做三件事（与方舟现有模式完全同构）：
1. **注入**：把 MAAOrch 的任务参数写成该引擎的配置文件（JSON）
2. **启动/停止**：进程管理（复用 runner 的启停/恢复链骨架）
3. **事件解析**：该引擎日志 → 适配器解析 → EventBus（完成/失败/体力/掉落信号）

不引入 MaaFramework Python 绑定直驱（选项 B/C 降级为备注）：引擎自带完整
能力，MAAOrch 只调配不代劳；规避 AGPL 代码传染（只写配置、不 import 其代码）。

## 3. 架构（对齐既有收敛方向）

```
编排层（游戏无关 — 已有，无需改）
  ├─ 调度台/任务参数化、launch_queue 队列+优先级+让位
  ├─ 实例池、模拟器池+状态机（EmulatorService）、恢复链
  ├─ 统计系统、账号体系（game_client 字段已预留）、EventBus
引擎层（MaaFramework — 统一，新引入）
  └─ Python 绑定（与 asst.py 同族）— 方舟/终末地/1999 共用
游戏资源层（task JSON/模板 — 每个游戏一份，复用社区适配）
  ├─ 方舟：现有 gui.json/tasks.json 注入体系（不动）
  ├─ 终末地：MaaEnd 的 task 资源（转换/引用）
  └─ 1999：M9A 的 task 资源（转换/引用）
适配层（每游戏一个，薄）
  ├─ task_defs   任务定义映射（MAAOrch 任务 ↔ 游戏 task 链）
  ├─ events      完成判定（游戏日志/回调 → EventBus）
  └─ controller  连接（模拟器 adb / PC 客户端窗口）
```

## 4. 推荐路径（试点先行）

- **阶段 0（铺垫，游戏无关，方舟也受益）**：适配器壳骨架抽象——
  把 runner 的「注入→启动→事件解析」抽成引擎适配器接口（不碰方舟
  现有链路，纯新抽象层）。
- **阶段 1（试点）**：**1999 先行**——M9A 是 Python（技术栈同族、
  日志可解析性强）；最小闭环=清日常验证「调配→引擎→判定→统计」管线。
- **阶段 2**：终末地（MaaEnd，配置/日志格式第二套适配）。
- **阶段 3**：编排层按 `game_client` 分流（队列/统计/恢复链），
  方舟链路不动。

- **License**：M9A/MaaEnd 均 **AGPL-3.0** —— 引 task 资源（JSON 数据/

  规避代码传染，需确认。
- 外部辅助不碰内存/注入（[[maa-plugin-vs-auxiliary]] B 路线）
- 跟随引擎最新版（[[maa-autoupdate-retry]] 教训；MaaEnd 4h 前更新=活跃）
- 适配器隔离：新增游戏不碰方舟现有链路（[[dev-prod-topology]]）
