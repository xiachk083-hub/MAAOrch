# 多游戏图像识别适配方案（终末地 / 重返未来 1999）

> 2026-08-14 立项调研：用户点名两个目标游戏。本文=生态现状 + 架构 + 路径，
> **未动工**（先出方案再动工铁律）。主线仍是方舟运营。

## 1. 生态调研（2026-08-14 实测 GitHub）

| 游戏 | 现成自动化项目 | 引擎 | 成熟度 |
|---|---|---|---|
| 终末地 | `AliceJump/ok-end-field`（534★，Python 3.12） | ok-script（ok-oldking 的 Windows UI 自动化框架：OCR/模板匹配/HSV） | 高：日常（礼物/兑换/委托）、体力本多难度、送货自动竞价+路线、仓库搬移、抽卡循环、实时战斗技能轮换、自动对话、拾取白名单、Windows 计划任务 |
| 重返未来 1999 | 无（仅 1 个 0★ Python 项目，未完成） | — | 空白 |
| MaaFramework 适配 | **两游戏均无 MaaXYZ 官方/社区适配** | — | 需从零写任务链 |

## 2. 结论：执行引擎选型修正

- 原方向「执行引擎优先评估 MaaFramework」（[[multi-game-vision-direction]]）——
  现实是**两个目标游戏都没有 MaaFramework 现成适配**，引入它=从零写任务链，
  与自研成本相同，还要承担框架学习/升级适配成本。
- **自研适配层是捷径**：MAAOrch 已有识别工具链天然游戏无关——
  PaddleOCR ONNX（[[local-ocr-tool]]）、模板匹配判定（StageProbe）、
  vision_translate 转译、模拟器控制（emu_service）——全部可直接复用。
- ok-end-field 的价值=**终末地任务地图参考**（玩法→任务定义），不依赖其代码。

## 3. 架构（对齐既有收敛方向）

```
编排层（游戏无关 — 已有，无需改）
  ├─ 调度台/任务参数化、launch_queue 队列+优先级+让位
  ├─ 实例池、模拟器池+状态机（EmulatorService）、恢复链
  ├─ 统计系统、账号体系（game_client 字段已预留）、EventBus
游戏适配层（新 — 每游戏一个，与方舟链路隔离）
  ├─ task_defs   任务定义（清日常/刷体力/抽卡/…）
  ├─ vision      ROI 布局 + 模板 + OCR 关键词（识别能力服务化后复用）
  ├─ controller  点击/滑动/模拟输入（模拟器 adb 或窗口句柄）
  └─ events      完成判定（识别信号 → EventBus，沿用 [[convergence-architecture-direction]]）
```

## 4. 推荐路径（试点先行，不并行开两条线）

- **阶段 0（铺垫，游戏无关，方舟也受益）**：识别能力服务化——
  OCR/截图/模板匹配抽成独立服务（= 5 方向计划第 4 项「辅助能力框架」，
  两件事是同一件，一起做）。
- **阶段 1（试点）**：重返未来 1999 适配器——2D 固定界面、回合制，
  识别难度最低，用最小闭环（清体力）验证「识别→点击→判定」管线。
- **阶段 2**：终末地适配器——参考 ok-end-field 任务地图，3D 场景
  识别难度高（视角/透视），先做固定界面部分（日常/商店/抽卡）。
- **阶段 3**：编排层按 `game_client` 分流（队列/统计/恢复链），
  方舟链路不动，新游戏走同一套调度。

## 5. 铁律延续

- 外部辅助不碰内存/注入（[[maa-plugin-vs-auxiliary]] B 路线）
- 跟随所用引擎最新版（[[maa-autoupdate-retry]] 教训）
- 适配器隔离：新增游戏不碰方舟现有链路（[[dev-prod-topology]] 生产敬畏）
- 识别判定必须可审计（截图/置信度留痕），不盲点
